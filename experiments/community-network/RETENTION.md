# What this desktop keeps

Open a chat and expand **On this device** to see its saved message count. Private and community chats both start at **All history**. As long as hosting is active, the desktop pages backwards from a permitted peer without needing the room open. A community member can switch to **Latest 500**. That removes older messages and their receipts from this device, including on the owner's device. The signed owner sequence, rather than download order, determines what is recent. Reading an older page doesn't evict newer history. Switching back can recover only what another authorized member still holds. The number counts saved messages, not bytes; it does not reserve disk space for attachments.

Room permissions still apply to each read. A member can briefly share while the owner is unavailable under the existing five-minute permission. The tracker has no room history, message IDs or per-room retention settings. If the only copy is removed, there is no server backup. SQLite can reuse freed pages; the database file need not immediately shrink.

In **Public posts**, **Follow** saves that device identity's public posts and replies, including older posts. No follow-back is needed. In **Your contribution → Public posts on this device**, review your follows and set the number of extra MB for posts by other people. It starts at zero. Lowering it releases volunteer copies first; unfollowing releases that author's copies from the follower archive. Publishing a post keeps your own original. The donation budget counts the actual serialized, signed record, not the zero-length media manifest on text posts. This is separate from media hosting and chat history. The desktop leaves 128 MiB of physical disk headroom for voluntary copies; a full disk can still prevent chosen archives from growing.

## What the tracker does

1. An active desktop signs a heartbeat with its route, remaining donated capacity, changes to the copies it holds, and a rotating inventory slice. A restarted desktop starts a new session; missed updates and lost tracker state reconcile in bounded batches. The author's own originals use the same batched inventory. One original per refresh rotates through the full publication path to help a restored index recover. A report lives for three minutes. A public post shows its recent seeders.
2. The tracker aims for three distinct online devices per public text post. It offers the rarest posts first, including posts with no online peer. Between equally scarce posts it favors the ones whose holders have been online at different times from the volunteer. It uses six four-hour UTC slots observed over the last seven days, then breaks ties randomly. This is an observation, not a promise about next week. No declared sleep schedule or explicit social graph is required. The operator can infer interests from author lookups and copy reports.
3. An offer reserves bytes and one target slot for 90 seconds. It counts as **zero available copies** until the recipient has verified and stored the signed post and reported it. Peers try recently online sources in shuffled order, using direct connections. The existing searchable registry already stores public text and can bootstrap it when all peer sources fail. It does not bootstrap private chats or media files.
4. A donor near capacity can exchange one community copy for a rarer post with zero or one recent seeder if two other devices were recently serving the old copy. A release reservation prevents simultaneous planned releases of the same post. The desktop fetches first and swaps within one SQLite transaction only if it can stay within budget. Following the old author in the meantime takes priority.
5. Returning devices and expired reservations trigger new opportunities on subsequent heartbeats. A paused or failing desktop is never required to finish a job. Last-seeder loss is still possible: devices can sleep together, refuse a request, or report an inaccurate inventory. There are no proofs of custody, multi-region durability guarantees, or unattended media placements in this beta.

The design borrows the idea of measured, bounded placement from [IPFS Cluster's allocation configuration](https://ipfscluster.io/documentation/reference/configuration/) and scarcity-first selection from [BitTorrent's original incentives paper](https://bittorrent.org/bittorrentecon.pdf). An additional IPFS daemon would not know our room permissions, follow choices or Iroh reachability. Keep the small allocator in the existing tracker for this 10,000-record beta. Revisit a separate allocator or paid always-on pins if measurements show repeated outages despite three reports, planning contention at the catalog limit, or a need for durable media guarantees.

To verify locally, run `cargo test -p community-network` from this experiment. The network flows start independent Iroh devices and a disposable tracker. They cover 507-message retention and recovery, directed follows, peer reads, repair after expiry, reserved capacity and time-slot selection.
