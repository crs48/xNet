This is the canonical log of xNet's architectural decisions. It is the one place
to answer "why is it built this way?" — superseding the older internal
`docs/TRADEOFFS.md`.

## How we keep this current

These records follow the standard [ADR](https://adr.github.io/) discipline:

- Every entry has a **Status**: `Proposed`, `Accepted`, `Deprecated`, or
  `Superseded by ADR-NN`.
- **Accepted ADRs are immutable.** We don't rewrite a decision when reality
  changes — we add a _new_ ADR that supersedes the old one and set the old
  entry's status to `Superseded by ADR-NN`. The truth of the architecture is the
  whole chain, not the latest entry. (Typo fixes, dead-link fixes, and adding a
  **Tripwire** are the only in-place edits.)
- **A one-way decision carries a Tripwire**: the observation that re-opens it.
  It is additive metadata, not part of the decision — it says nothing about what
  was chosen, only what would make us write the superseding ADR. Without one, a
  decision decays into a taboo: the rationale ages, the conditions that produced
  it change, and because nobody wrote down what would count as evidence against,
  the entry stops being re-openable and becomes a rule nobody remembers the
  reason for. This is the same job `review:` does for `docs/explorations/`
  (exploration 0421), and the reasoning is exploration 0430's.
- **If an implemented change alters an architectural invariant, it adds or
  supersedes an ADR in the same PR.** Most decisions are worked out first in
  `docs/explorations/`; this page is the distilled outcome.

## ADR-1: Yjs over Automerge for rich text

**Status:** Accepted (2026-02) · scope clarified by [ADR-11](#adr-11-xnet-is-a-protocol--the-interop-kernel-is-the-change-log-not-yjs)

**Decision:** Use Yjs for rich text CRDT, not Automerge.

**Rationale:**

- Yjs has a larger ecosystem (TipTap, ProseMirror, CodeMirror, Monaco integrations)
- Better performance for large documents (Yjs encodes more compactly)
- Mature awareness protocol for cursor presence
- Active maintenance and wide adoption

**Tradeoff:** Yjs is a mutable data structure (not pure-functional like Automerge). We mitigate this with the MetaBridge pattern — Yjs never writes to the NodeStore directly.

**Scope note:** Yjs is the **document codec** for the rich-text/canvas _body_ of
certain nodes — it is _not_ the sync backbone. Structured node data syncs through
the signed `Change<T>` log ([ADR-3](#adr-3-field-level-lww-for-structured-data)),
and Yjs updates ride the wire as opaque bytes inside an xNet envelope. See
[ADR-11](#adr-11-xnet-is-a-protocol--the-interop-kernel-is-the-change-log-not-yjs).

## ADR-2: DID:key for identity

**Status:** Accepted (2026-02)

**Decision:** Use `did:key` (Ed25519) as the identity format.

**Rationale:**

- Self-certifying — the public key is embedded in the DID, so verification requires no external resolver
- No blockchain, registry, or server dependency
- Small identifiers (~56 characters)
- Ed25519 is widely supported and audited

**Tradeoff:** DIDs are not human-readable. Display names are stored as profile metadata, not in the identifier itself. Key rotation requires creating a new DID (though UCAN delegation can bridge old and new identities). Account recovery is handled by social recovery — see [ADR-24](#adr-24-social-recovery-via-shamir-guardians).

## ADR-3: Field-level LWW for structured data

**Status:** Accepted (2026-02) · this is normative protocol L1 — see [ADR-11](#adr-11-xnet-is-a-protocol--the-interop-kernel-is-the-change-log-not-yjs)

**Decision:** Use Lamport clocks with field-level last-writer-wins for structured data, not a CRDT map.

**Rationale:**

- Simpler than a full CRDT for property data (titles, statuses, numbers)
- Field-level granularity means non-conflicting fields always merge cleanly
- Deterministic tie-breaking (DID comparison) ensures all peers converge
- Lower overhead than maintaining CRDT metadata per field

**Tradeoff:** True concurrent edits to the same field result in one write being silently dropped. In practice, this is acceptable for structured properties — users rarely edit the same title simultaneously. For rich text where character-level merging matters, Yjs handles it.

## ADR-4: BLAKE3 over SHA-256

**Status:** Accepted (2026-02) · post-quantum posture in [ADR-25](#adr-25-post-quantum-migration-posture)

**Decision:** Use BLAKE3 as the primary hash function.

**Rationale:**

- 3-5x faster than SHA-256 on modern hardware
- 256-bit output suitable for content addressing
- Parallelizable (tree hashing) for large inputs
- No length extension attacks

**Tradeoff:** SHA-256 has wider interoperability (most external systems expect it). We provide SHA-256 as a fallback option in `@xnetjs/crypto` for interop cases.

## ADR-5: Named exports only

**Status:** Accepted (2026-02)

**Decision:** No default exports anywhere in the codebase.

**Rationale:**

- Eliminates the "what did I import?" ambiguity
- Better tree-shaking in bundlers
- Consistent import style across the monorepo
- Easier to search for usages (grep for the exact name)

## ADR-6: Factory functions alongside classes

**Status:** Accepted (2026-02)

**Decision:** Export `createFoo()` factory functions alongside `class Foo`.

**Rationale:**

- Factory functions are easier to mock in tests
- They can perform validation before construction
- Consistent API surface (`createLamportClock`, `createExtensionContext`, `createLocalAPI`)
- Classes are still available for `instanceof` checks when needed

## ADR-7: Validation returns, not exceptions

**Status:** Accepted (2026-02)

**Decision:** Validation functions return `{ valid: boolean, errors: string[] }` instead of throwing.

**Rationale:**

- Callers can inspect and aggregate errors
- No try-catch boilerplate for expected failures
- Works well with UI form validation
- Exceptions are reserved for programmer errors (missing arguments, broken invariants)

## ADR-8: One-way MetaBridge

**Status:** Accepted (2026-02) · MetaBridge now ships in `@xnetjs/runtime` — see [ADR-14](#adr-14-framework-agnostic-runtime--react-is-a-thin-binding)

**Decision:** The MetaBridge syncs NodeStore → Y.Doc metadata, but not the reverse.

**Rationale:**

- Prevents malicious Yjs updates from poisoning structured data
- Property changes always go through the signed `Change<T>` pipeline with verification
- Yjs metadata map is read-only from the editor's perspective
- Clear security boundary between the two CRDT systems

**Tradeoff:** Two-way sync would be simpler to implement. The one-way bridge requires property writes to go through `mutate()` even when the data is displayed in the editor context.

## ADR-9: Multiplexed WebSocket

**Status:** Accepted (2026-02) · extended to multi-home routing in [ADR-20](#adr-20-namespace-scoped-multi-home-replication)

**Decision:** Use a single WebSocket connection with room-based pub/sub, not one connection per document.

**Rationale:**

- O(1) connections regardless of document count
- Reduces server-side resource usage
- Simpler reconnection logic (one connection to restore)
- Lower latency (no connection setup per document)

**Tradeoff:** Requires a room routing layer on top of raw WebSocket. The signaling server must track topic subscriptions.

## ADR-10: BSM in Electron main process

**Status:** Accepted (2026-02)

**Decision:** Run the sync engine in Electron's main process, not the renderer.

**Rationale:**

- Keeps the renderer responsive (BLAKE3 + Ed25519 are CPU-intensive)
- Survives renderer crashes
- Can sync in the background when no window is open
- MessagePort provides zero-copy binary transfer between processes

**Tradeoff:** IPC overhead for every document update. Mitigated by using `MessageChannelMain` for binary transfer and batching updates. (A migration from Electron to a Deno-based desktop shell has been explored but not adopted.)

## ADR-11: xNet is a protocol — the interop kernel is the change log, not Yjs

**Status:** Accepted (2026-06)
**Context:** Exploration 0200. The normative spec lives in `docs/specs/protocol/`; see also [The Protocol](/docs/protocol/overview/).

**Decision:** Treat xNet as a versioned, multi-implementation **protocol** whose
normative surface is four layers — **L0** cryptographic primitives, **L1** data
model, **L2** replication, **L3** authorization — with the application profile
(**L4**) explicitly non-normative. The interop kernel is a **signed,
hash-chained, per-property-LWW change log over schema-typed nodes**
(`CURRENT_PROTOCOL_VERSION = 3` in `packages/sync/src/change.ts`). Yjs is a
**pluggable document codec** for the rich-text/canvas body of certain nodes and
travels the wire as opaque bytes inside an xNet envelope.

**Rationale:**

- A second implementation, in any language over any database, can forward and
  store the Yjs blob as an octet string and still fully participate in the node
  graph, identity, authorization, and replication — the hardest local-first
  portability problem (porting a CRDT byte format across languages) is off the
  critical path.
- The boundaries already existed in the layered package graph; this decision
  writes them down and freezes them behind a conformance corpus.

**Tradeoff:** Two merge systems (the LWW log and the Yjs CRDT) instead of one.
Accepted deliberately — they have different conflict semantics and scale
profiles (see [ADR-1](#adr-1-yjs-over-automerge-for-rich-text) and
[ADR-3](#adr-3-field-level-lww-for-structured-data)). This ADR clarifies ADR-1
and elevates ADR-3 to normative status.

**Tripwire:** a second implementation cannot fully participate in L0–L3 while
treating the Yjs body as an opaque octet string — i.e. some normative behaviour
turns out to require decoding the document bytes. That would mean the codec is
not pluggable and the kernel boundary is drawn in the wrong place.

## ADR-12: SQLite everywhere — better-sqlite3 + Litestream, not Turso/libSQL

**Status:** Accepted (2026-06)
**Context:** Explorations 0178 (hosting economics) and 0212 (engine merits).

**Decision:** Keep SQLite as the durable storage substrate across all five
runtimes behind one adapter (`@xnetjs/sqlite`). On the web, persist via
**OPFS + SQLite WASM** in a single serial worker; on the hub, use
**better-sqlite3 with Litestream** streaming replication to Cloudflare R2
(`packages/hub/src/storage/litestream.ts`). Do **not** migrate to libSQL or
Turso Database.

**Rationale:**

- xNet barely uses SQLite as a relational database — the schema is an append-only,
  signed, hash-chained change log with a denormalized scalar index; graph walks
  and CRDT merges happen in TypeScript/Rust, not SQL. Most of Turso's advances
  (query planner, relational concurrency) are low-leverage here.
- The two features that _would_ tempt us (embedded vector ANN, concurrent
  writes) live in two different Turso products, neither production-ready together
  today; migrating would cost five platform adapters and an FTS5 rewrite.
- FTS5 and R-Tree/GIS (which we _do_ use) are battle-tested on SQLite.

**Tradeoff:** Single-writer serialization and no built-in vector index. A bounded
Turso pilot on the disposable `telemetry.db` is sanctioned as a probe.

**Tripwire:** one engine ships production-ready embedded vector ANN **and** MVCC
concurrent writes together (today they live in two different Turso products), or
a shipped feature needs a vector workload SQLite + FTS5 demonstrably cannot
serve.

## ADR-13: Local-first — the hub is an accelerant, never a dependency

**Status:** Accepted (2026-06)
**Context:** Exploration 0188. See also [Local-first](/docs/concepts/local-first/).

**Decision:** The local device holds the master copy. Nothing on a hub or the
network may block a local read or first paint; hub work (relay, backup, search,
signaling) is fire-and-forget and strictly additive.

**Rationale:**

- Local-first is the product's core promise (own your data, work offline, exit
  freely) — it must be an enforced invariant, not an aspiration.
- A regression where hub room-subscription blocked document load caused
  10–30s stalls; the fix (decouple local load from hub acquisition) codified the
  rule.

**Tradeoff:** Some cross-device features are eventually-consistent rather than
instantly authoritative. Accepted: correctness comes from the convergent LWW log,
so "eventually" is safe.

**Tripwire:** a shipped feature cannot produce its first paint without a hub
round-trip — not "is slower offline", but _cannot render_. One such feature makes
the hub a dependency in fact regardless of what this entry says, and the honest
move is to supersede rather than carry a promise the product no longer keeps.

## ADR-14: Framework-agnostic runtime — React is a thin binding

**Status:** Accepted (2026-06)
**Context:** Explorations 0185 and 0237.

**Decision:** The full client — store, MetaBridge, SyncManager, NodePool,
Registry, OfflineQueue, ConnectionManager — lives in the React-free
`@xnetjs/runtime` package. `createXNetClient()` and `liveQuery()` expose a
universal `{ getSnapshot, subscribe }` contract. `@xnetjs/react` is a thin **T1**
binding (`useQuery`/`useMutate`/…) that re-exports the runtime. Support tiers:
**T0** any framework/vanilla (the runtime, ships today), **T1** React
(first-party), **T2** Vue/Svelte/Solid (demand-gated, ~40-line adapters).

**Rationale:**

- The reactive seam is tiny — only two files in `@xnetjs/react` touch
  `useSyncExternalStore`; everything else is business logic and JSX.
- Decoupling lets the runtime power CLIs, servers, and non-React apps without a
  React dependency.

**Tradeoff:** "Support" for a framework means feature parity, not just a data
binding — the ~30k LOC of `@xnetjs/react` is the real cost. So T2 adapters are
published only on demand, and only the data hooks (not `@xnetjs/ui`) are in scope.

## ADR-15: Open-core license split — MIT core, FSL cloud, MIT-private contract

**Status:** Accepted (2026-06)
**Context:** Exploration 0181.

**Decision:** Publish the adoption engine (core packages) under **MIT**. License
the managed control plane, `@xnetjs/cloud`, under **FSL-1.1** (source-available,
converting to Apache-2.0 on its Change Date; `packages/cloud/LICENSE`). Keep the
entitlement contract in a separate, permissively-licensed `@xnetjs/entitlements`
(MIT, `private`) so the self-hostable MIT hub can verify a signed `HUB_PLAN`
token without ever taking an FSL — or a Stripe/AWS — dependency.

**Rationale:**

- The hub must remain fully MIT and dependency-light; the cloud must be
  protectable. The entitlement contract is the one seam both sides share.
- FSL protects against a hyperscaler reselling the managed service while
  guaranteeing eventual open-source (the Apache future license).

**Tradeoff:** A three-package licensing story is more to explain than "all MIT" or
"all FSL." The `@xnetjs/hub` package deliberately has zero dependency on
`@xnetjs/cloud`; that separation is by convention (and verified by the absence of
the import), not yet a lint rule.

**Tripwire:** the MIT hub acquires a dependency on FSL-licensed code (which
`pnpm check:cloud-boundary` would catch first), or a hyperscaler ships a managed
xNet anyway — proving FSL bought no protection and only cost adoption.

## ADR-16: Automated releases via Changesets + Conventional Commits

**Status:** Accepted (2026-06)
**Context:** Exploration 0220.

**Decision:** Version and publish with [Changesets](https://github.com/changesets/changesets).
A `fixed` group of 12 core packages (`core`, `crypto`, `identity`, `sync`,
`data`, `storage`, `sqlite`, `data-bridge`, `abuse`, `plugins`, `history`,
`react`) versions in lockstep; periphery versions independently. Conventional
Commits are enforced by commitlint; publishing uses npm Trusted Publishing (OIDC)
with provenance. Changeset coverage for publishable packages is enforced by a Stop
hook (`scripts/changeset/assert-coverage.mjs`).

**Rationale:**

- The `fixed` core avoids a combinatorial version matrix across tightly-coupled
  packages; independent periphery avoids forcing churn on loosely-coupled ones.
- OIDC removes long-lived npm tokens from the repo.

**Tradeoff:** The semver bump must be read from the _diff_, not the commit prefix
(a removed export or changed wire contract is a major even under a `feat:`
commit). This requires discipline the hook can prompt for but not fully decide.

## ADR-17: Plugin trust and capability model

**Status:** Accepted (2026-06)
**Context:** Explorations 0189, 0192, 0194, 0196.

**Decision:** Extensibility is governed by a shared trust fabric. `@xnetjs/trust`
maps install **provenance** (`builtin` / `authored` / `ai-generated` / `imported`
/ `marketplace` / `synced`) to a **trust tier** and a **sandbox kind**
(`host` / `ses-worker` / `iframe`). Capability endowments are enforced at the
seam — `guardStore` gates data access, `guardedFetch` gates the network
(SSRF-guarded) in `@xnetjs/plugins`. Paid plugins carry Ed25519, DID-bound
license tokens (`@xnetjs/licenses`) with a **fail-closed** install gate.

**Rationale:**

- "Everything is a plugin" only works if untrusted code is contained by
  construction; provenance is the natural axis for how much to trust.
- Fail-closed licensing means a missing or invalid license blocks install, never
  silently downgrades.

**Tradeoff:** More ceremony for plugin authors (declared capabilities, sandbox
constraints) in exchange for a substrate that can safely run third-party and
AI-generated code.

## ADR-18: Managed AI via hub broker, plus bring-your-own local models

**Status:** Accepted (2026-06)
**Context:** Explorations 0201, 0208, 0244, 0252.

**Decision:** For managed AI, the client uses a **keyless** `ManagedProvider`
that POSTs to the hub's `/ai/chat` (+ `/ai/chat/stream` SSE); the hub injects
tenant credentials, holds the OpenRouter key, and meters exact `usage.cost`
server-side (`packages/hub/src/features/ai-forwarder.ts`). In parallel, a
bring-your-own path runs models **locally** — WebLLM in-browser and Chrome's
built-in "Nano" via an `availability()` probe (`packages/plugins/src/ai/`).

**Rationale:**

- Keyless managed AI means no provider key ever reaches the client; the hub is
  the metering and margin-safety boundary.
- Local models give a zero-cost, fully-private tier that needs no hub at all,
  consistent with [ADR-13](#adr-13-local-first--the-hub-is-an-accelerant-never-a-dependency).

**Tradeoff:** Two provider code paths to maintain, and local-model availability
varies by browser/hardware. Detection is capability-probed, not assumed.

**Tripwire:** a provider worth routing to requires a key on the client (the
keyless property is the whole boundary), or local models reach parity such that
the managed path exists only to meter — at which point it is a billing decision
wearing an architecture costume.

## ADR-19: Plan-first AI mutations

**Status:** Accepted (2026-06)
**Context:** `docs/AI_SURFACE_CONTRACT.md`.

**Decision:** AI never writes directly. The shared AI surface expresses writes as
an `AiMutationPlan` that must move through **validate → preview → apply → audit**.
Every tool declares `requiredScopes` and a risk level (`low`/`medium`/`high`/
`critical`); plans are serializable JSON so they flow identically through MCP,
the Local API, file projection, and audit logs.

**Rationale:**

- A plan-first pipeline makes AI writes reviewable and reversible, and keeps one
  contract across every adapter.
- Risk levels + scopes let the UI gate high-consequence actions
  (`storage.recovery` requires `critical`).

**Tradeoff:** More indirection than letting an agent call `mutate()` directly, in
exchange for auditable, user-approvable, rollback-friendly AI edits.

## ADR-20: Namespace-scoped multi-home replication

**Status:** Accepted (2026-06) · extends [ADR-9](#adr-9-multiplexed-websocket)
**Context:** Exploration 0258.

**Decision:** Sync routes selectively per **namespace**. A multiplexed multi-hub
connection manager (`packages/runtime/src/sync/connection-manager.ts`) maintains
one connection per hub; a replication-policy planner
(`packages/sync/src/replication-policy.ts`) decides which namespaces replicate to
which hubs/peers, with per-namespace `minHubs`/`maxHubs` and signed-replication
requirements. A user-facing **Space** maps to a namespace via `spaceNamespace()`,
carrying a `ReplicaTrust` of `trusted` or `zero-knowledge`
(`packages/runtime/src/sync/replication-scope.ts`).

**Rationale:**

- Different data belongs in different homes (system vs personal vs community vs
  peer); routing by namespace is the smallest primitive that expresses that.
- Correctness is free — the multi-master LWW log already converges regardless of
  topology; this decision is about _where_ bytes go, not _whether_ they merge.

**Tradeoff:** Only the routing slice is shipped; the manifest schema, device DID,
anti-entropy, trust gating, and UI are deferred. The planner exists ahead of full
consumption.

**Tripwire:** a real replication policy needs a unit finer than a namespace (per
node, per schema) or coarser (per account), or the planner is still unconsumed by
the time the manifest and trust gating ship — built-ahead machinery that never
acquires a caller is the shape this repo already knows from 0377.

## ADR-21: Append-only change log with off-boot compaction

**Status:** Accepted (2026-06)
**Context:** Explorations 0204, 0254, 0260.

**Decision:** Never delete from the change log; append tombstones and materialize
current state. Reclaim space with **compaction that runs off the boot path** —
gated behind `runWhenBootSettled` (resolves at first-rows), using tiny
loop-until-dry chunks that bail on a hidden tab
(`apps/web/src/lib/change-log-compaction.ts`). The web runtime funnels all SQLite
work through one serial worker with a priority scheduler.

**Rationale:**

- The append-only log makes sync trivial and gives a complete audit trail; but an
  unbounded log inflates cold-start.
- On a single serial SQLite worker, **no background work is free during boot** —
  `requestIdleCallback` tracks main-thread idle, which is idle precisely while the
  worker is saturated. Scheduling maintenance _after_ boot settles is the only
  reliable fix; priority reorders work, it never parallelizes it.

**Tradeoff:** Reclamation is deferred rather than immediate, and compaction is
best-effort (bails on backgrounded tabs). Accepted: a responsive cold open
outranks prompt disk reclaim. Compaction stays default-on, opt-out via
`xnet:compact:changes='off'`.

**Tripwire:** compaction stops keeping up — the change log grows monotonically
across a release cycle on an ordinary workload — or cold open breaches
exploration 0266's stop rule (first rows under 100ms p95) with compaction already
default-on. Either means deferred reclamation has stopped being free, which is
the entire basis of this entry.

## ADR-22: Consent-gated observability

**Status:** Accepted (2026-06)
**Context:** Exploration 0210.

**Decision:** Zero telemetry by default. Error monitoring (Sentry) and analytics
(Plausible) initialize only when _both_ a build-time endpoint is configured
(`VITE_SENTRY_DSN` / `VITE_ANALYTICS_DOMAIN`) _and_ the runtime consent tier
allows it (`packages/telemetry/src/consent/manager.ts`;
`apps/web/src/lib/{sentry,analytics,error-reporter}.ts`). Reports are scrubbed and
values are P3A-bucketed.

**Rationale:**

- Decentralized, own-your-data software must not phone home without explicit,
  granular consent; gating at both build and runtime makes "off" the safe default.

**Tradeoff:** Far less diagnostic data (users rarely opt in), so we lean on
reproducible boot timelines and local forensics instead of always-on telemetry.

## ADR-23: Values-as-code CI gates

**Status:** Accepted (2026-06)
**Context:** Explorations 0199 (motion) and 0234 (humane charter).

**Decision:** Encode the product's values as enforced lints, not just prose. A
motion-vocabulary gate (`scripts/check-motion-vocab.mjs`) bans ad-hoc animation
outside the approved vocabulary; a humane-patterns gate
(`scripts/check-humane-patterns.mjs`) bans dark patterns (infinite scroll,
streaks, engagement-maximizing nudges). Both sit alongside the Humane Internet
Charter (`docs/CHARTER.md`) and a real "Right to Leave" export-everything panel.

**Rationale:**

- A stated value that CI can't defend drifts. Mechanizing "calm" and "no dark
  patterns" makes them regression-proof and legible to skeptics.

**Tradeoff:** Some legitimate UI needs a documented exception path around the
gates. Accepted: the friction is the point — it forces the intent to be explicit.

## ADR-24: Social recovery via Shamir guardians

**Status:** Accepted (2026-06)
**Context:** Exploration 0243.

**Decision:** Recover an identity through **Shamir-split guardian shares**
(`packages/identity/src/recoverable.ts`) — a threshold of trusted guardians
reconstructs the key — alongside recovery phrases and synced passkeys. The cloud
is never a custodian. Custodial escrow was explicitly **declined**.

**Rationale:**

- `did:key` has no built-in rotation ([ADR-2](#adr-2-didkey-for-identity)), so
  recovery must live outside the key itself.
- Custodial escrow is coercible (subpoena, insider, breach); social recovery
  keeps trust distributed and cloud-free.

**Tradeoff:** Recovery depends on the user having designated reachable guardians
ahead of time. Accepted as the price of a non-coercible, self-sovereign model.

## ADR-25: Post-quantum migration posture

**Status:** Proposed
**Context:** Exploration 0257; the future path for [ADR-4](#adr-4-blake3-over-sha-256) and [ADR-2](#adr-2-didkey-for-identity).

**Decision (proposed):** Adopt a phased migration to post-quantum signatures —
Phase 2 hybrid (Ed25519 + ML-DSA), Phase 3 ML-DSA primary with Ed25519 legacy —
behind an algorithm-agility seam, rather than a flag-day switch.

**Rationale:**

- Ed25519 is broken by Shor's algorithm; a hash-chained, signed log needs a
  credible PQ story before it's a compliance blocker.
- Hybrid signatures preserve interop during the transition.

**Tradeoff / open:** Larger signatures and a two-algorithm verification path. This
is a documented _posture_, not shipped code — it stays `Proposed` until the seam
and hybrid signing land, at which point it is superseded by an `Accepted` ADR.

## ADR-26: Cross-hub grants — plane split before propagation

**Status:** Accepted (design); implementation deferred to a follow-up
**Context:** Explorations 0258/0382/0383 (W4). Hub-to-hub Space subscription
shipped for **public** Spaces; grants do not cross hubs.

**Decision:** Cross-hub access control splits by plane before any grant ever
propagates. The **public plane** needs no grants: a hub mirrors another hub's
public Space over the ordinary wire protocol, and mirrored state is **never
re-exported** (served only under `/sub/*`), so subscription cycles cannot
amplify. The **granted plane** stays single-hub until a dedicated design lands:
a grant is a capability minted by a Space's home hub, and no mirror, gateway,
or federation surface may widen it. When cross-hub grants are built, they will
be **delegation chains rooted at the granting hub's persistent DID** (UCAN-style,
matching the existing auth kernel) — never grant-table replication, which would
turn every subscribed hub into a policy-enforcement point it cannot honestly be.

**Rationale:**

- Public-first delivered the hub-of-hubs primitive without touching the
  security kernel (0383's subscription-first ordering).
- Replicating grant rows would make revocation eventually-consistent across
  hubs an attacker can choose among — a deny must always win (0359).
- Delegation chains keep the home hub authoritative: a downstream hub can
  _prove_ access was granted without being able to _mint_ it.

**Tradeoff:** Members of a gated community cannot yet read it through a
different hub. Accepted: correctness of revocation outranks read locality.

## ADR-27: `@xnetjs/server` stays a separate product

**Status:** Accepted
**Context:** Exploration 0382/0383 (the standing question): "everything is a
hub" unified the server surface into one binary with roles — except
`@xnetjs/server`, the BYO-backend engine (exploration 0223), which does not
depend on `@xnetjs/hub` at all.

**Decision:** **Scope out.** `@xnetjs/server` is not a hub role and will not
be absorbed. It serves a different buyer: an app team embedding xNet's data
model inside _their_ backend (their auth, their storage, their trust mode) —
not an operator running xNet's server. The hub's role system covers every
deployment of _our_ server; `@xnetjs/server` remains the library for building
_someone else's_.

**Rationale:**

- Absorbing it as a role would couple its `TrustMode`/storage hooks to hub
  release cadence for zero operator benefit (the MinIO gateway lesson, 0382:
  a role that cannot share the core's invariants is a neighbour, not a role).
- The decision is recorded precisely so the "second server" cannot drift back
  into ambiguity one layer up (0383 R6).

**Tradeoff:** Two server documentation surfaces. Accepted; they answer
different questions.

**Tripwire:** `@xnetjs/server`'s `TrustMode` and storage hooks converge with the
hub's until a role _could_ share the core's invariants (the 0382 test for
neighbour vs role), or the BYO-backend buyer fails to materialise — nobody
embeds it in their own backend — at which point maintaining a second server is
paying for an audience that does not exist.

## ADR-28: No durable-execution orchestrator; reconcilers instead

**Status:** Accepted
**Context:** Exploration 0411 evaluated adopting [Temporal](https://temporal.io/)
(and Restate, DBOS, `pg_durable`, Inngest, Cloudflare Workflows) for the parts
of the stack that look workflow-shaped: tenant provisioning, staged fleet
rollouts, nightly restore drills, and the non-payment lifecycle.

**Decision:** **Do not adopt a workflow engine.** Fix the three real durability
gaps in-repo with primitives over the `DocStore` port the control plane already
ships — a compensating `saga()`, a leased due-based job runner, and a durable
`RolloutRun` checkpoint.

**A workflow engine may only ever be considered for `apps/cloud`.** It must
never enter `packages/hub`, `packages/server`, or any client package.

**Rationale:**

- Temporal and its peers provide durable _execution_; xNet's hard problem is
  durable _state_, which CRDTs and the signed change log already solve. The
  position was already recorded in exploration 0332's landscape survey.
- It cannot run where most xNet work happens. The Temporal TypeScript SDK runs
  workflow code in a Node-only deterministic sandbox against a server cluster —
  there is no browser or offline story, and the device is xNet's primary.
- In `packages/hub` it would break a Charter §6 receipt ("the hub is a single
  self-contained process"), failing the **BATNA** test: a self-hoster would have
  to operate a workflow cluster to run their own hub.
- The control plane is deliberately built as pure decision functions plus
  level-triggered reconcilers, which are restart-safe by construction. Only two
  modules deviated, and both were ordinary bugs rather than a missing capability.
- Every candidate bottoms out in a datastore we do not run. There is no Postgres
  anywhere in the stack (SQLite + Firestore only), so the usual "just use DBOS"
  answer is unavailable.

**Tradeoff:** We maintain ~300 lines of scheduling and compensation logic
ourselves. Accepted, and bounded.

**Tripwire:** any of the six decidable tripwires recorded in exploration 0411,
or the hand-rolled primitives (`saga()`, the leased job runner, the `RolloutRun`
checkpoint) growing past ~500 LOC — at which point we are maintaining the thing
we declined to adopt, without its testing or its operator tooling.

## ADR-29: xNet is not an agent harness

**Status:** Accepted
**Context:** Exploration 0416 asked whether xNet should connect to agent
harnesses (OpenClaw, Hermes, Buzz) or build a competing one with its own
privacy layer. "Agent harness" turned out to name three separate jobs, two of
which xNet already occupies in shipped code: the **substrate** agents act
against (`xnet mcp serve`, Agent Passports, the audit trail — exploration 0337) and the **client** that drives an agent (the bridge daemon and
`AgentFrame` wire — exploration 0392). Only the third — owning the agent loop
itself, with channels, scheduling, memory, and a skill marketplace — was
genuinely undecided.

**Decision:** **Do not build an agent harness.** xNet is the _accountability
substrate_ agents run against and a _client_ for the good ones. The agent loop,
its messaging channels, its cron and heartbeats, and its skill marketplace are
permanent non-goals.

The corollary is a positive commitment: the guardrail, the passport, and the
audit ledger stay **xNet-side** and apply identically to every connected agent,
regardless of what that agent's own permission model claims.

**Rationale:**

- **The layer commoditised.** Five meta-harnesses landed in roughly one week of
  June 2026 — Databricks Omnigent (Apache-2.0), Zed ACP, Vercel HarnessAgent,
  Cloudflare Flue, and Conductor — on top of two excellent free harnesses
  (Hermes, MIT; OpenClaw). Nothing xNet builds here stays differentiated for a
  quarter.
- **The layer beneath it did not.** OpenClaw's audit is mutable JSONL with
  documented blind spots for cron jobs and sub-agents; Hermes records learned
  capability in `SKILL.md` but says nothing about attribution. xNet's kernel —
  `authorDID`, per-author `parentHash` chains, Ed25519 signatures — answers
  "prove what the agent did" structurally, and exploration 0337 already aimed
  it at agents.
- **Composition beats competition.** Positioned beneath every harness, xNet
  works with all of them. Positioned as one, it competes with all of them and
  composes with none — including Buzz, whose agents already carry keypairs and
  are a natural interop target rather than a rival.
- **A harness is a permanent treadmill.** Every model release re-opens the
  work, and the skill-marketplace supply chain brings a ClawHavoc-class trust
  problem xNet has no advantage in solving.

**Tradeoff:** xNet's relationship with the user is mediated by whichever agent
they chose, so the accountability story has to be marketed as the reason the
agent is _safe_ rather than as a product of its own. Accepted: the alternative
spends the roadmap's other two pillars on a layer five funded competitors gave
away in one week.

**Scope note:** the provider-agnostic loop in
`packages/cloud/src/ai/agent-runner.ts` stays — it is a _safety core_ (tool
allow-list, injection deny point, token-cap breaker) for xNet's own server-side
features, not the seed of a harness product.

**Tripwire:** growing `agent-runner.ts` channels, scheduling, or a skill
registry — the three things that would make it a harness. Separately, the
commoditisation premise fails if the layer re-consolidates: two of the five June
2026 meta-harnesses dead and one harness holding a dominant share of agent
sessions for two consecutive quarters would mean "nothing stays differentiated
for a quarter" was wrong, and the substrate-only position needs re-arguing.

## ADR-30: Hub addresses resolve; no data-path routing tier

**Status:** Accepted
**Context:** Exploration 0423 compared xNet's managed fleet to PlanetScale's
account of hiding 768 database servers behind one connection string. xNet
already runs that topology — `packages/cloud/src/provisioner/sharding.ts` places
800 tenant hubs per GCP project — and pays almost none of the router tax,
because its shard key is a person and people do not join to each other: no
cross-shard queries, no resharding, no rebalancing.

What xNet had not bought was the other half of what the router provides. The
Cloud Run adapter returns `hubUrl: svc.uri`, so a client's durable configuration
is a vendor hostname. A region move, a substrate swap, or a migration to
self-hosting silently misconfigures every device — defeating, at the last inch,
the `Provisioner` abstraction that exists so xNet is never hostage to one
vendor's terms.

**Decision:** Give hubs a stable name that **resolves** to an address the client
dials directly. **Never** operate a proxy, gateway, or load-balanced routing
tier that xNet-hosted traffic passes through.

Concretely: a hub publishes a record signed by its own system identity at
`/.well-known/xnet-hub-address`; the control plane may **mirror** that record
but never authors one; the client resolves once, caches, and falls back to its
last-known address when the resolver is unreachable.

**Rationale:**

- A gateway fails the Charter §6 **BATNA** test outright — a self-hoster cannot
  run the routing tier, so the self-hosted path becomes measurably worse than
  the managed one.
- It fails the **Vanish** test — if xNet disappeared, every client would be
  pointed at a hostname resolving to nothing, mid-session, with no local
  fallback. A resolution record degrades instead to "connect where you connected
  last time", and the address travels inside the `.xnetpack` export.
- The Charter already refuses this by name: _"No global chokepoint tier. We do
  not operate an indispensable middle to rent back later."_ A tier carrying
  every byte of every tenant's sync traffic is that middle, described.
- Signing matters because mirroring is allowed. A mirror that could rewrite
  `url` would be a redirect primitive for anyone who compromised it; re-serving
  the hub's signature verbatim makes the mirror untrusted by construction.
- The split between the signed record (**where** to connect) and the mirror's
  unsigned liveness hint (**whether to wait**) is deliberate: a lying mirror can
  make a client pause, never redirect it.

**Tradeoff:** Not _quite_ one connection string — a migration costs one failed
dial and a re-resolve, and the client needs a cache-invalidation story. Accepted:
a one-round-trip staleness window is far cheaper than an operated tier we have
promised not to build.

**Tripwire:** any proposal to terminate tenant sync connections on
xNet-operated infrastructure — including for fleet-wide rate limiting or
observability, the usual framings — re-opens this ADR rather than shipping under
it.

## ADR-31: The operational record runs on xNet; readings do not

**Status:** Accepted
**Context:** Exploration 0431 found the control plane has no audit log at all —
`/internal/*` sits behind one flat shared secret, and `POST
/internal/account/recover` clears a tenant's bound DID so the next device to
present a passkey claims their hub. Anyone holding the secret could take over any
tenant and leave no attributable trace. The hub, meanwhile, already has what the
control plane lacks: `packages/hub/src/routes/audit.ts` pages an author's signed,
hash-chained change history.

**Decision:** Operator actions, incident notes and consent grants are **signed
xNet nodes** authored by an operator's bound `did:key`, so the change log _is_
the audit trail. They live on a dedicated ops hub, run through the managed GCP
path in **its own project**, and **never** provisioned by the fleet provisioner.

Metrics and tenant state stay in Firestore. SLI buckets are hourly writes per
tenant forever — exploration 0323 measured a 318k-row change log producing a
multi-second cold-open stall, and a 250-change burst cliff above which every
subscribed client re-renders. `TenantRecord` stays authoritative in Firestore
because billing and provisioning read it on the request path.

Audit is **two-tier**: a fail-closed Firestore write authorises the action, and
the signed node publishes asynchronously.

**Rationale:**

- A signed change log is _verifiable_; an append-only database collection is
  merely _trusted_. With a signing identity an operator cannot repudiate an
  action and nobody with database access can forge one.
- The ops hub must not share fate with the fleet it records. Its own project,
  outside the provisioner, means a fleet-provisioner bug — the realistic failure
  for a small team — cannot destroy the record of what operators did.
- Two tiers resolve the contradiction between "audit before acting" and "the hub
  may be unreachable during an incident". Tier 1 never blocks on the hub, so
  operators can always act; the publish queue's depth is an alertable metric, so
  a gap between the tiers is visible rather than silent.
- The record is low-volume by construction. Keeping the readings off it is what
  makes the ops hub something that never needs to scale.

**Tradeoff:** The ops hub becomes a standing dependency of incident response, and
the audit trail is eventually-consistent rather than synchronous. Accepted: the
local replica and the tier-1 gate mean the degraded mode is "audit history is
stale", not "you cannot see or do anything".

**Tripwire:** the ops hub's change log crosses ~100k changes, or any proposal to
put a per-tenant time series on it — either re-opens the record/readings split
rather than shipping under this ADR.

## ADR-32: Support sees shape; content requires per-incident consent

**Status:** Accepted
**Context:** A managed hub is not opaque to its operator. The trusted tier
provides integrity and revocation-denial but **not** confidentiality
(exploration 0343), and `packages/hub/src/services/search-indexer.ts` extracts
plaintext from rich text to build the FTS index. Any support console therefore
draws its boundary in policy and audit, not in cryptography — and four
user-facing surfaces were claiming otherwise.

**Decision:** Operators see **Tier 1 — shape** without consent: counts, bytes,
latencies, plan, region, version, sync backlog, job history, error class and
stack. No document titles, no field values.

**Tier 2 — content** requires a typed reason, the tenant's explicit grant, and a
hard expiry with no renewal. Every request, grant, denial and expiry is mirrored
to the tenant's own hub. **Standing consent is refused at every tier, including
enterprise contracts.**

Audit is graduated: aggregate fleet views are not audited, per-tenant reads are
audited silently without a prompt, mutations require a typed reason. Audit
entries are retained 12 months and are **not** purged when a tenant is deleted.

**Rationale:**

- Most real tickets — "is my sync broken", "why is my hub slow", "where did my
  storage go" — are answerable from shape alone. Making content expensive and
  visible rather than impossible is what keeps the boundary honest instead of
  routinely circumvented.
- Titles are not a soft middle ground. A document called "Q3 layoffs" leaks
  exactly the thing the boundary protects.
- A reason prompt on every read trains operators to type "investigating", which
  produces a log that looks rigorous and means nothing. Reserving the prompt for
  mutations keeps it meaningful.
- Standing access is the mechanism by which consented access erodes into routine
  unlogged looking. Refusing it at contract level is the only durable form.
- Audit surviving tenant deletion protects the _user_: it is the only thing
  preventing look-then-delete from erasing its own evidence.

**Tradeoff:** Some tickets will be slower, and some enterprise negotiations will
be harder. Accepted: a sovereignty promise with a standing-access carve-out is
not a promise.

**Tripwire:** the first support ticket that cannot be resolved at Tier 1, or the
first enterprise negotiation that makes standing access a condition of sale —
either re-opens the consent model rather than shipping an exception under it.

## ADR-33: Storage is sold as a flat per-GB add-on, not a plan tier

**Status:** Accepted
**Context:** Exploration 0435 asked whether a customer could buy 100, 500 or
1000 GB while keeping everything else about their plan unchanged. The
entitlement machinery already supported it — `withStorage()` and
`requiresMigration()` treat a quota change inside an isolation tier as a live
flip — but two things did not. Bulk bytes were written to the hub's local
filesystem, which on Cloud Run is an in-memory tmpfs capped at 32 GiB, so the
catalog's existing `company` (1 TiB) and `enterprise` (5 TiB) quotas were
already unbuildable. And `quotaBytes` is enforced **per user**, so a pack sold
once per tenant would have been provisioned once per seat.

Welding storage to the plan tier had also produced a live inversion: `family`
($15/mo) shipped 250 GiB while the strictly more expensive, more isolated `team`
tier shipped 100 GiB.

**Decision:** Sell storage as an **additive per-tenant add-on at a flat
$0.03/GiB-month** — +100 GB $3, +500 GB $15, +1000 GB $30 — billed as a second
Stripe `SubscriptionItem`, never as a new plan tier and never per seat.

Three invariants make it safe:

- **The pack is stored; the quota is derived.** `TenantRecord.storagePackGb`
  holds the purchase and every resolve recomputes `planBase + pack`. Persisting
  a resolved absolute would make a `personal`+500 GiB tenant upgrading to
  `family` silently shrink from 750 GiB to 525.
- **Enforced against a per-tenant ceiling.** `tenantQuotaBytes` is a new signed
  field, absent meaning unlimited, so the pack is not multiplied by seat count.
- **Billing leads the entitlement.** The Stripe webhook applies the flip, so
  held space always equals billed space.

**Rationale:**

- **It is the cleanest improvement charge xNet has.** Every GB sold is a GB
  rented from Cloudflare at $0.015 and replicated, monitored and backed up. The
  margin rides on an operation we run, not on access to bytes the customer would
  own anyway — Charter §6's improvement test, passed more squarely than by seats
  or AI markup.
- **The BATNA is real and stays real.** Keeping data local is free and
  unlimited, export is free, egress is zero, and the same MIT hub self-hosts
  against the customer's own bucket. Consumer clouds sell 2 TB below our raw
  input cost; the honest answer to that comparison is bring-your-own-bucket, not
  a price war we would lose.
- **A flat rate over a linear cost holds one margin.** 42% at every pack size —
  one number to defend, no volume-discount cliff, and a floor-margin test that
  fails if a future edit tiers the price.
- **Per-seat storage was rejected twice over.** It would smuggle back the
  per-member meter `withSeats()` refuses for `community` (0359), and it prices
  out the single-seat customer with a 1 TB archive, who is the actual demand.

**Tradeoff:** $0.03/GiB is roughly six times iCloud's headline rate, and the
comparison will be made. Accepted: we are selling capacity inside a live,
synced, exportable hub, and the customer who only wants a cheap byte locker
should use one.

**Tripwire:** if storage becomes a material share of revenue, the incentive to
degrade local-first storage appears. The first proposal to cap on-device
storage, throttle local sync, or slow export for large workspaces re-opens this
decision — charging for cloud bytes is an improvement charge only for as long as
**not** buying them remains fully functional. Separately, R2 Infrequent Access
at $0.010/GiB would make a lower published rate viable; a sustained gap between
our price and blended COGS is a reason to cut the price, not to bank the margin.

## ADR-34: A tenant is a roster of DIDs, and the hub enforces it

**Status:** Accepted
**Context:** xNet Cloud provisioned hubs but had no model of who was inside one.
`TenantRecord` held a single `billingUserId` and a single `did`; there was no
invite, roster, role or removal anywhere in the control plane. Meanwhile the hub
applies a trusted-root policy only when `config.trustedDids` is set
(`packages/hub/src/auth/ucan.ts`), and the control plane never set it — so a
self-issued UCAN from a key generated seconds ago was accepted on a hub somebody
else was paying for. `seats` had exactly two consumers in the whole repository,
both render calls (exploration 0436).

**Decision:** A tenant carries `members: TenantMember[]` — `{ did, role,
addedAtMs, addedBy }` — and that roster is the trusted-root policy. It projects
into `HUB_TRUSTED_DIDS` on every entitlement push, including inside
`bindDataIdentity`, so a device that has just claimed a hub is trusted before it
is told to connect.

Three invariants make it safe:

- **Absent means legacy, not empty.** A record written before `members` existed
  reports `[{ did, role: 'owner' }]`. `rosterFor()` is the only place that
  decides this.
- **An empty policy is never written.** `checkTrustedRoots` treats absent and
  empty identically, so an empty value produces a hub that is wide open while
  looking configured. `trustedDidsEnv()` returns `undefined` rather than `''`.
- **A self-hosted hub never receives the variable at all**, so its behaviour is
  unchanged — the anti-lock-in invariant from ADR-4 / exploration 0174.

Invitation reuses the device grant rather than inventing a second handshake: the
collaborator's app shows a short code, the owner approves it, and the key is
minted on their own device. An invited DID joins the roster **without** rebinding
the tenant.

**Rationale:**

- The hub's authorization model is rich and correct — grants, spaces, roles, the
  CRUD split. What was missing sat one layer above it: nothing decided which DIDs
  _are_ the tenant. Admission control and seat counting are the same missing
  concept wearing a security hat and a product hat.
- Putting the roster in the control plane rather than in the hub's own grants
  keeps it readable during a support call and during a GDPR request, and lets a
  member join while the owner is offline.
- Modelling a tenant as a WorkOS Organization was rejected: a WorkOS user is an
  email an IdP vouches for and a member is a key on someone's device, and
  conflating them would put the billing identity provider in charge of the data
  identity — the arrangement the non-custodial claim flow exists to avoid.
  `organizationId` is a pointer that decides who is _entitled_ to join; each
  human still binds their own key.

**Tradeoff:** membership changes push a new revision, which on Cloud Run restarts
the hub — invisible on scale-to-zero plans, a brief rolling drop on warm ones.
Accepted: the alternative is a hub anyone on the internet can write to.

**Tripwire:** the first proposal to authorize on the roster _instead of_ the hub's
grant model — the roster decides admission, never permission — or the first hub
shipped with `HUB_TRUSTED_DIDS` written as an empty string. Either re-opens this.

## ADR-35: Seats bill collaborators, never audience

**Status:** Accepted
**Context:** `team` was advertised at `$12/seat/mo` from three seats while
`checkout.sessions.create` passed `quantity: 1`, so a three-seat subscription
billed $12 against a margin model assuming $36. With ADR-33 the roster makes a
seat countable for the first time, which is exactly when somebody will want to
bill it by length (exploration 0436).

**Decision:** Seats are a real Stripe `SubscriptionItem.quantity`, floored at the
plan's catalog minimum and kept in sync from `customer.subscription.updated` by
reading the subscription **item** rather than the checkout metadata — metadata
records what was bought and never moves when a customer adds a seat later.

Two limits are part of the decision, not implementation detail:

- **`guest` never consumes a seat.** `seatsUsed()` counts owners and members
  only. A seat is capacity we provision for a collaborator; an audience member
  the customer brought is not one.
- **Flat plans are never multiplied.** `checkoutQuantity` returns `1` for any
  plan with `seats === 0`, and `withSeats()` already refuses to attach a seat
  count to `community`.

Enforcement refuses **admission** and never evicts a live session: a tenant at
its seat limit cannot invite a fourth person, and the three already there keep
working.

**Rationale (Charter §6):**

- **Improvement** — a seat is a collaborator whose devices sync against a hub we
  operate: real connections, real storage, real relay.
- **BATNA** — self-host the MIT hub with unlimited members; `@xnetjs/entitlements`
  is MIT and dependency-free, so a self-hosted hub never phones home.
- **Vanish** — every member's authoritative copy is on their own device. Losing
  the hub loses the relay, not the data.
- Disconnecting someone mid-sync reads as data loss in a local-first product even
  when it technically is not, which is why the guard is admission-time only.

**Tradeoff:** a tenant can sit at its seat limit with people waiting, and the fix
is a plan change rather than an automatic overage charge. Accepted: a surprise
bill is the failure mode the AI budget work already went out of its way to
prevent.

**Tripwire:** _the moment a seat is charged for someone the customer brought
rather than someone we provision capacity for, this decision is void._ The
concrete signals are a proposal to seat-meter `community`, or to count
read-only/guest DIDs as seats on any plan. The roster is where that would sneak
in, because once you have a member list somebody will want to bill its length.

## ADR-36: A host may refuse service; refusal never takes the work

**Status:** Accepted · 2026-08-13 · exploration 0444

**Context:** Every account-suspension story in the industry follows one shape. A
platform reads what a customer stored, decides against them, and in the same
motion stops serving them and keeps their work. The two are separable acts —
Google left a father's account closed after police cleared him; Notion terminated
a workspace it had to read in order to judge; Slack cut off researchers with no
window to pack; Google banned Gemini subscribers in February 2026 over a
third-party OAuth integration with no appeal and no refund. Nothing technical
fuses judgement to custody. They arrive together because the account is the only
handle anyone built, so pulling it drags everything attached.

xNet Cloud is a host. It will receive abuse reports, legal demands and sanctions
lists, and sometimes the honest answer is no. A promise never to refuse anyone
would be worth nothing and would be broken inside a year, so the promise has to
be the other one.

**Decision:** A host may refuse service. A host may never turn refusal into a
claim on the customer's work.

Concretely, and already true in code: every action moderation can take names
**reach** — `reject`, `hide`, `quarantine`, `block-peer`
(`packages/abuse/src/policy-blocks.ts`) — and none names possession. There is no
`delete`, no `revoke`, no `confiscate`. An appeal resolves to `reverse` or
`annotate` (`packages/abuse/src/appeals.ts`), and `reverse` is only a meaningful
word because nothing was destroyed. Identity is a `did:key` the host neither
issues nor can revoke (`packages/identity/src/keys.ts`); the wire format is an
open signed hash-chained log another hub can pick up (`packages/sync/src/change.ts`);
the client runs with no hub at all (`packages/runtime/src/sync/offline-queue.ts`).

**Rationale (Charter §1, §2):** the master copy is the customer's, so a refusal
withdraws a relay rather than a possession. This is what makes Exit true at the
one moment it matters — the moment you are no longer welcome. An export flow that
only works while you can still log in is not an exit; it is a door on an interior
wall.

**Tradeoff:** a hub cannot make a bad actor's data disappear from their own
device, because it never had it to begin with. Refusal stops propagation and
stops us relaying, and that is the whole of what a host can honestly offer.
Accepted: the alternative is a capability that, once it exists, is available to
every future operator, subpoena and acquirer of this company.

**Tripwire:** _the moment any hub role gains an action that removes a user's data
rather than restricting its reach, this decision is void._ The concrete signals
are a `delete`, `purge`, `revoke` or `confiscate` member on `PolicyBlockAction`, a
moderation path that writes to storage rather than to a policy list, or a
retention job that treats suspension as a deletion trigger. Quota and dormancy
reclamation are the honest place this sneaks in, because there the deletion has
an operator's reason and no villain attached.

## ADR-37: Native desktop recovery preserves whole workspace generations

**Status:** Accepted · 2026-09-29 · exploration 0466

**Context:** A desktop upgrade can change storage while the same Mac holds the only
copy of a workspace. A database dump alone omits blobs, imported source files, and
the desktop identity needed to use the data.

**Decision:** The local `xnet-desktop-checkpoint/1` format stores a manifest and a
complete copy of `xnet-data`. Its manifest names the app version, profile, identity
mode, and every file's size and SHA-256 hash. Both SQLite stores must pass an
integrity check. Production copies require the stored identity seed. Test copies
are explicitly marked and cannot restore a daily workspace.

A copy becomes available only after verification and an atomic directory rename.
Restore verifies it again, stages a new generation, and records a durable journal
before renaming directories. Startup finishes that journal before opening any
store. The replaced generation remains available separately from the last twenty
recovery copies. An installer waits for saved text, closed stores, and a verified
copy before running.

**Tradeoff:** These are local recovery copies, not encrypted portable backups.
They exclude Chromium settings and sign-in sessions. Platform-encrypted keys still
need the same Mac's key store. Losing the disk loses these copies too. The product
must state this scope until separate off-device and cross-Mac recovery are proven.

**Tripwire:** A persistent file moves outside `xnet-data`, a database changes its
storage format, or recovery must work on a different Mac. Any of these reopens the
manifest scope and restore protocol before a broader protection claim ships.

## ADR-38: Retain source evidence separately from imported social records

**Status:** Accepted · 2026-09-29 · exploration 0466

**Context:** Social exports change shape. Parser fixes need the original evidence,
and a file selected for preview may change before an import begins.

**Decision:** Before its first node write, a desktop import retains the entire
selected file under `xnet-data/import-sources/<sha256>/source.zip` or `source.json`.
The copied bytes must match the preview fingerprint. Promotion is atomic and
files are private to the local user. Reimports reuse verified bytes. Originals
are never moved or deleted. The import screen states that unselected categories
remain in this private source copy, though only selected categories become nodes.
Native recovery includes this directory.

GitHub captures use the JSON wrapper `xnet-github-stars/1`: account, capture start
and finish, endpoint/media type/API version, coverage, and raw star rows. A finished
paginated capture records `paginationCompleted: true` and `atomic: false`. Native
repository IDs identify resources; native star times identify observed activity.
Missing times stay missing. An absent repository never implies an unstar event.

**Tradeoff:** Retaining raw exports costs disk space and keeps more private data
than the selected graph alone. Credentials are not part of the GitHub snapshot.
This format provides evidence for retries; it does not itself make a job resumable
or turn local recovery into an off-device backup.

**Tripwire:** A source cannot be represented as exact retained bytes, evidence
needs selective deletion, or import resume requires a different source contract.
Revisit custody and migration before changing the format or retention promise.

## ADR-39: Validate desktop upgrades on a separate workspace generation

**Status:** Accepted · 2026-09-29 · exploration 0466

**Context:** A known older database needs an upgrade path without making the only
copy the migration's test subject. Recovery also needs to run while the app stays
open for days.

**Decision:** The desktop supports candidate migration from the oldest tested
historical schema, currently version 8, through the current schema. Before any
normal store opens, validate identity and pin a verified original checkpoint.
Apply every registered SQL step to a separate copy. Validate the resulting column
contract, existing row counts, foreign keys, and integrity before promotion
through the durable restore journal. Keep the replaced generation. Unknown,
earlier, future, or unreadable formats stop in recovery without writes to their
database. A promoted workspace pauses automatic network services for review.

The native checkpoint manifest gains optional `sourceFingerprint`, `storageVersion`,
and `pinned` fields. `appVersion` names the app that made the copy, not a promise
that every app with that version can open its contents. The scheduler checks once
a minute, copying changed data when fifteen minutes overdue. This supersedes
ADR-37's flat twenty-copy retention: keep one point per fifteen-minute bucket for
a day, per day for a week, and per week for four weeks, plus the latest two.
Pinned points and preserved originals are not pruned automatically. Pruning still
requires a newly verified point, and copy failures remain visible in the app.

**Tradeoff:** Backups can briefly delay editing, pinned originals consume space,
and only tested historical versions migrate automatically. Native copies still
exclude browser settings and need the same Mac key store. This decision adds no
portable or off-device guarantee.

**Tripwire:** A migration changes existing row contents, the oldest supported
version changes, or checkpoint time/storage use disrupts daily work. Add the
relevant historical fixture and data-preservation proof before widening support
or changing the displayed recovery policy.

## ADR-40: Portable desktop recovery carries encrypted identity and source bytes

**Status:** Accepted · 2026-09-29 · exploration 0466

**Context:** Copying native recovery files to another disk does not make their
Keychain-encrypted identity usable on another Mac. Losing the original machine
must not make the only surviving backup useless.

**Decision:** `xnet-desktop-portable/1` is a directory containing a small public
header, an encrypted manifest, and encrypted file chunks. The password derives
a 32-byte key with scrypt (N=131072, r=8, p=1, random 32-byte salt). Each object
uses native AES-256-GCM with a fresh random 12-byte nonce, a 16-byte tag, and the
format identifier as authenticated data. File chunks are at most four MiB.
The authenticated manifest binds ordered ciphertext hashes to each original
path, size, and plaintext SHA-256. It also carries the actual desktop signing
seed and any stored recovery mnemonic, encrypted under the recovery password.
The public header contains no filenames, identity, or password.

Export starts from a verified native checkpoint and verifies the encrypted
manifest and every object before atomically publishing the folder. Restore
extracts only into a new private directory, verifies files and databases, and
rewraps the same seed using the destination key store. A fresh native checkpoint
records those changed key-file bytes. Only then may the existing restore journal
replace the workspace, preserving its prior generation and pausing networking.
The desktop currently accepts portable restores for the current storage version;
an incompatible backup fails before changing live files.

**Tradeoff:** Password loss is unrecoverable. This format has no password escrow,
compression, or incremental deduplication. Browser settings and sign-in sessions
remain excluded. The app verifies written bytes but cannot infer that a chosen
folder is off-device. It must state that distinction. Tests with different mock
key stores and a real desktop round trip do not prove a second physical Mac or
signed installer continuity.

**Tripwire:** A cryptographic parameter changes, a required key lives outside
this manifest, a supported backup needs migration during restore, or large
exports block normal desktop use. Reopen the format and recovery evidence before
changing the reader or broadening the protection claim.

## ADR-41: Resume archive imports from retained evidence and acknowledged batches

**Status:** Accepted · 2026-09-29 · exploration 0466

**Context:** An in-memory progress bar cannot continue an import after a restart.
Retaining an archive alone does not record which categories were reviewed or
which writes completed.

**Decision:** Desktop imports retain a version-1 journal under
`xnet-data/import-jobs`. It records the reviewed stage, adapter version, source
hash and extension, original import time, source-record policy, author DID, and
acknowledged progress. Private signing keys are never written to this journal.
Each journal update uses a private temporary file, fsync, and atomic rename.
The cursor advances only after the database acknowledges the batch.

An interrupted running job appears paused after startup. Resume requires the
same workspace identity and importer version, verifies the retained source, and
replays its stable stream through the last saved cursor. Previously acknowledged
batches are skipped. A crash after a database commit but before the journal update
may replay one batch using deterministic node IDs. This provides at-least-once
writes, not an exactly-once claim. A changed importer requires fresh review.
Native and encrypted recovery include the journal and source together; source
paths are resolved against the restored workspace, not the original machine.

**Tradeoff:** Resume reparses the earlier source records to reconstruct its
position. A damaged journal fails visibly rather than appearing as an empty job
list. Old adapter versions are not bundled indefinitely, and progress from older
in-memory-only imports cannot be recovered automatically.

**Tripwire:** An importer no longer emits a stable stream for identical bytes,
an import gains non-idempotent effects, or its batch boundary changes. Version
the journal or importer and prove replay safety before accepting old cursors.

## ADR-42: Desktop enrichment keeps full evidence in a recoverable local store

**Status:** Accepted · 2026-09-29 · exploration 0466

**Context:** Social card fields have size limits. Putting a video description or
transcript only in those fields silently loses searchable text. A browser queue
also cannot reliably survive a desktop restart or carry work into a recovery copy.

**Decision:** `xnet-data/library.db`, SQLite user version 1, stores full metadata,
caption cues, provider evidence, FTS search rows, and durable capability jobs.
Job identity includes resource ID, capability, provider version, and language.
Metadata, thumbnails, transcripts, and indexing have separate outcomes. Missing
fields and failed discovery stay explicit. Interrupted work returns to the queue;
provider backoff and pause state survive restart. Fetching starts only after the
user enables enrichment and remains disabled during recovery review.

Source resources stay in NodeStore. Bounded SocialEnrichment card projections and
versioned transcript segments link back to those resources; they do not replace
full evidence. Thumbnail bytes live in the existing managed blob store. The
Library reads cached images, full descriptions, and caption matches offline.
List responses exclude raw evidence and full transcripts; details load on demand.

Native checkpoints freeze enrichment and include the library database with its
committed WAL content. Portable recovery includes it through the same manifest.
Library compatibility is checked before any startup migration or writable open.
A damaged or unknown library format requires recovery rather than reconstruction.

**Tradeoff:** The full-text store is device-local and is not yet synced between
peers. Caption retrieval currently uses the explicitly tested local yt-dlp
version; login-limited sources remain blocked. This decision does not claim local
ASR, whole-corpus enrichment, or packaged helper installation. Full source evidence
costs disk space, and schema upgrades need copied fixtures before support expands.

**Tripwire:** Another device must receive full enriched text, provider evidence
outgrows practical backups, or a library schema/provider upgrade invalidates
stored work. Revisit the storage boundary and migration proof before changing it.

## ADR-43: Captured notes are private Pages with explicit source relations

**Status:** Accepted · 2026-09-29 · exploration 0466

**Context:** Saving a URL with an observation should create something editable.
Importers and metadata refreshes must not own or replace the user's writing.
A crash between creating a Page and saving its document must leave a recoverable
intent rather than an unexplained empty note.

**Decision:** Page gains the optional `sourceResources` relation. Capture reuses
a matching social resource and creates a separate private Page with its own Yjs
text, original URL, optional excerpt, and source relation. A second note is an
explicit new capture. The relation grants no access to either endpoint and does
not publish the resource or Page.

The desktop writes a version-1 capture intent to `library.db` before creating
nodes. Its stable request ID binds the exact input, author DID, resource ID,
Page ID, and initial document bytes. Success requires acknowledged node and
text writes plus local search indexing. Repeating a request resumes that intent;
it never overwrites an existing document. Startup resumes incomplete intents
under the workspace write barrier. The journal is included in native and portable
recovery and contains no signing key.

The shared workbench hosts the form through an optional host capability. Desktop
provides the native save and URL lookup. A failed attempt keeps the original
payload fixed for retry; successful saves unlock the normal Page editor. Desktop
capture uses Command/Ctrl+Shift+L, reads clipboard text only when invoked, and
returns to the prior foreground application on macOS when capture finishes.

**Tradeoff:** Capture spans recoverable steps rather than one cross-database
transaction. The intent retains a copy of the original writing. Unsaved form
text lives in the browser profile until Save creates a native intent; it is not
part of the portable-backup claim. Other hosts may implement the same optional
capability later. Source relations must be reviewed by the separate publishing
path before a guide is exported.

**Tripwire:** Capture starts editing an existing Page, source relations imply
sharing permissions, or a new document format changes replay. Revisit request
identity, privacy checks, and interrupted-save tests before expanding the path.

## ADR-44: Observe committed local writes without applying them twice

**Status:** Accepted · 2026-09-29 · exploration 0466

**Context:** The desktop utility process imports and enriches records while the
renderer keeps a NodeStore open over the same database. The renderer previously
ignored native change notifications and kept its startup change clock. A later
title edit could receive an older timestamp and lose to an already-saved import.

**Decision:** Every local change allocation advances from the persisted Lamport
time as well as the instance's current time. An unreadable stored clock fails the
write. `NodeStore.refreshPersistedNodes(ids)` reads committed records through the
store's read boundary and notifies subscribers without writing them again. It
rejects missing or unreadable records. Refresh events are marked remote so sync
listeners do not rebroadcast them. Native notifications carry only IDs into this
API; supplied notification properties are never used as authoritative content.

Desktop subscribes to its existing native change channel, refreshes in bounded
groups, and retains failed groups for another notification or the end of a write
barrier. Refresh errors remain visible. A notification is not a save receipt; the
native write acknowledgement remains the persistence boundary.

**Tradeoff:** Clock allocation gains a storage read. This prevents sequential
writers from using stale clocks; it does not serialize overlapping writes from
two NodeStore instances. Native mutation barriers and stronger concurrent-writer
validation remain separate work. The API requires all requested records to be
readable, and is for stores sharing the same underlying committed state.

**Tripwire:** Concurrent native and renderer mutations overwrite one another,
clock reads measurably harm typing or imports, or a remote transport starts using
this API. Revisit single-writer ownership or atomic allocation before widening
the guarantee.

## ADR-45: Recover desktop settings through an encrypted logical snapshot

**Status:** Accepted · 2026-09-30 · exploration 0466

**Context:** Native workspace copies omitted browser-held preferences, provider
keys, and an unfinished capture draft. Copying Chromium directories would bind
recovery to browser internals and device session keys.

**Decision:** `desktop-settings.json` stores a version-1, bounded, explicit map
of desktop setting names to strings or null. Main encrypts it with `safeStorage`
and acknowledges a private atomic write only after file and directory fsync. The
renderer save barrier includes this snapshot. Missing settings are distinct from
unreadable settings, and unreadable prior copies cannot be overwritten.

`xnet-desktop-portable/2` carries the logical snapshot inside its authenticated,
password-encrypted manifest and rewraps the native file for the destination key
store. The manifest and checkpoint inventory must agree about its presence. The
reader still accepts version 1 with its original coverage. Older readers reject
version 2. This extends the coverage limits recorded in ADR-40 and ADR-43; their
original format and capture contracts remain historical decisions.

Restore applies the map before importing settings consumers. A unique restore
generation and browser receipt prevent normal restarts from replaying an older
snapshot over newer edits. A failed application retries before app startup.
Device-bound passkeys, session wrapping keys, cookies, test flags, temporary
OAuth verifiers, and bridge authorization tokens are excluded. Desktop signing
identity still comes from the native seed.

**Tradeoff:** The explicit list needs maintenance as desktop settings grow. The
copy protects values at a completed checkpoint, not every subsequent draft edit.
Existing browser APIs still hold their normal values in Chromium; this decision
encrypts the recovery copy rather than moving all live credentials into a vault.

**Tripwire:** A new non-reconstructible desktop key or setting appears outside
the list, an identity flow starts using IndexedDB as its authoritative store, or
restore receipts can replay stale settings over later edits. Extend the versioned
contract and failure tests before broadening the recovery claim.

## ADR-46: Drain workspace watches before disposing their storage

**Status:** Accepted · 2026-09-30 · exploration 0466 verification

**Context:** Closing a workspace watch stopped future timers but left its current
scan writing review files. The CLI could dispose storage while an asynchronous
scan callback was still applying edits. Full-suite cleanup exposed this race.

**Decision:** Keep the synchronous watch handle's `close()` contract and add
`AiWorkspaceWatcher.waitForIdle()`. Callers close their handles, then await this
method before disposing storage or removing the checkout. The drain includes
both scans and their asynchronous callbacks. Each watch serializes scans.
Background failures stop that watch, log the failure, and remain available as an
`AggregateError` from the drain. The CLI follows this order on Ctrl-C and exits
with failure when draining or disposal fails.

**Tradeoff:** Closing alone does not wait. A callback that never settles can hold
shutdown open; forcing process exit would abandon work and cannot claim a clean
shutdown. The method covers watch-dispatched work, not independent explicit scans.

**Tripwire:** A caller needs bounded cancellation, parallel scans become necessary,
or any consumer disposes storage before awaiting the drain. Revisit ownership and
cancellation semantics before changing the shutdown guarantee.

## ADR-47: Pair spatial Library viewers with an ephemeral read capability

**Status:** Accepted · 2026-10-06 · exploration 0468

**Context:** A headset browser cannot use Electron's preload. Exposing the general
local API or development server would give the viewer capabilities it does not need.

**Decision:** The owner starts a separate HTTPS listener from the desktop graph,
explicitly choosing the visible saved links and a certificate already trusted by
both devices. Only private-network clients are accepted. The listener serves a
compiled browser viewer and a frozen, revision-matched graph/layout projection.
A random 256-bit invitation in the URL fragment can be redeemed once within five
minutes for an in-memory bearer capability. The capability expires one hour after
creation or immediately when the owner revokes access, the app exits, or the
listener stops. Credentials are never logged or persisted by the viewer.

The only data routes are snapshot, bounded search, selected-resource details and
thumbnails resolved through those resources. No arbitrary blob IDs, conversations,
personal notes, identity material, SQL, writes or enrichment jobs are exposed.
Details are a bounded projection; longer saved source text or transcript text is
requested explicitly and limited to 100,000 characters. Reads check revocation
again after asynchronous storage access. Exact host and origin checks, no CORS,
no-store responses and a same-origin content policy constrain browser access.

**Tradeoff:** This is an experimental, session-local transport, not an independent
synced Library or a supported durable public protocol. Users must provision trust
and address resolution on both devices. A copied capability authorizes its holder
until expiry or revocation; it is not a hardware-bound device credential. Revocation
stops future reads but cannot erase content already delivered to a device.

**Tripwire:** We need internet access, persistent pairing, offline private content,
multiple readers, or native clients consuming a stable protocol. Revisit the
capability and ownership design before extending this experimental transport.

## ADR-48: Render chat extensions against explicitly granted xNet records

**Status:** Accepted · 2026-10-19 · chat prototype

**Context:** The chat extension prototype accepted message strings and returned a
layout tree. Extensions need real xNet hooks without inheriting the host's entire
store, identity, or network access.

**Decision:** Add `@xnetjs/react/queries`, exposing the existing `useQuery` and a
`DataBridgeProvider` for hosts that already own their bridge. This provider is a
context boundary, not an authorization mechanism. Existing `XNetProvider` consumers
continue to use the same context.

Chat extensions run pinned React, xNet schemas, `useQuery`, and selected UI primitives
in a terminable worker inside an opaque-origin iframe. The host resolves explicit
read grants before sending bounded record snapshots. Grants are local to the owner,
conversation, and source/compiler/runtime hash. Selected conversations include future
messages; personal tasks and pages require individual record selection. Relations
never confer access to their targets. The first implementation permits Channel,
ChatMessage, Task, and Page properties, with no document bodies, writes, identity
APIs, arbitrary imports, or network. Updates rerender the view; revocation cancels
rendering, unsubscribes, clears the view, and removes the saved grant.

The worker uses React server rendering and converts inert markup into a validated
text/layout tree. The host never evaluates extension code or inserts its HTML.
CSP denies network in the opaque frame and worker. Runtime compilation requires
eval only inside that isolated worker, never in the host renderer.

**Tradeoff:** These are read-only views, not interactive React applications: effects,
event handlers, document editors, custom schemas, and mutation hooks are not supported.
Limits fail explicitly instead of presenting truncated data as complete: 200 records
per selection, 500 total, 256 KB of input, and a two-second rendering deadline.
Revocation stops future delivery but cannot erase previously observed content.

**Tripwire:** An extension needs mutations, interactive state, custom schemas, larger
collections, network access, or shared installations. Revisit the capability protocol
and runtime before expanding privileges or relaxing isolation and resource limits.

## ADR-49: Guard extension edits at the storage boundary

**Status:** Accepted · 2026-10-19 · local chat prototype; extension protocol experimental

**Context:** ADR-48's tripwire was reached: extensions need real React state,
events, and mutation hooks. Checking a grant in the renderer does not protect
against a record being changed while a write is awaiting storage.

**Decision:** Add optional snapshot preconditions and an absolute deadline to
NodeStore and DataBridge transactions. Every touched ID must have a condition;
callers also include records on which their authorization decision depends.
An adapter must explicitly support conditional batches. Unsupported adapters,
including encrypted paths without atomic support, reject the command. Memory
and native Electron compare snapshots before applying changes; SQLite compares
fixed record/property rows inside the write transaction. Electron conditional
batches never use the chunked bulk-import path. Ordinary transactions retain
their existing behavior. Guarded deletes return committed tombstones.

The local chat prototype uses a persistent React worker, Remote DOM's polyfill,
and a closed text/layout/button/text-input receiver. It reuses actual `useQuery`
and `useMutate` through a narrow DataBridge. The host binds a command channel to
the current owner, artifact grant, and runtime session. Requests cannot choose
these values. Private task writes require separate approval; editable fields
are title, status, completion, priority, and due date. No relation, ownership,
visibility, or shared-container changes are permitted. New tasks are private.
Undo compares the committed receipt snapshot and fails on later edits.

**Tradeoff:** This is not the full API contract proposed in exploration 0481.
Receipts and replay protection are session-local. Revocation immediately stops
admitting commands and delivering data, then drains previously accepted commits
before reporting completion. It cannot recall committed edits or previously
observed data. Grants remain local device preferences; no remote delegation is
implemented. A worker can be terminated but has no hard heap isolation.
Documents, network, agents, schemas, files, and native access remain unavailable.

**Tripwire:** Before permitting shared destinations, durable background execution,
remote installations, raw document updates, or arbitrary third-party code, move
all relevant grant/dependency state to the authoritative commit boundary and
obtain an independent review. Do not extrapolate the private-task checks to
community permissions or claim the entire 0481 security model is implemented.

## ADR-50: Couple local extension grants and receipts to conditional commits

**Status:** Accepted · 2026-10-19 · local prototype; extension SDK remains experimental

**Context:** ADR-49's session approvals and receipts could not survive a restart or
prevent another session from committing against a revoked approval. Documents
also need a separate read boundary from page properties.

**Decision:** Extend conditional transactions with bounded compare-and-swap
entries in device-local app state and an optional absent-key durable receipt.
The storage owner records the result and change heads alongside node writes in
one atomic commit. Adapters opt into this feature explicitly. Empty node batches
still execute their local-state checks and writes. Neither grants nor receipts
are synced as ordinary records, and the untrusted bridge exposes no local-state
reader or writer.

An extension approval binds owner, conversation, artifact hash, and a fresh epoch.
Revocation persists an inactive record; reopening or reverting source cannot
reactivate that epoch. Commands bind their identifier and payload to that approval;
a lost response can be recovered without repeating the effect. Created task scope
and the last receipt persist. A new approval creates a new epoch. Host permission
reads distinguish absence from unavailable or corrupt storage. Previous localStorage
approvals are not imported automatically.

Document text has a separate exact-page read grant, with opaque session handles.
The host projects current visible text from acquired documents, omitting resource
attributes, nested embeds, and deleted history. The extension receives no Y.Doc,
awareness object, editor plugin context, or document persistence method. Raw updates
and document editing require a further authority-aware commit path.

**Tradeoff:** This establishes device-local authority, not cross-device revocation
or independent security certification. Foreground sessions recheck before data
and results are delivered and poll for idle cross-window revocation. Revocation
cannot erase already observed text. Browser workers still lack hard heap isolation.
A grant permits at most 1,000 committed commands before a new approval; old receipt
keys remain bound to their retired epoch. Storage rollback by a device owner is
outside this model.

**Tripwire:** Before document writes, shared destinations, background jobs, or remote
delegation, extend the same commit boundary to document versions and every relevant
membership/disclosure dependency. A public stable SDK requires an independent review.

## ADR-51: Commit scoped document edits through a durable local overlay

**Status:** Accepted · 2026-10-20 · local prototype; extension SDK remains experimental

**Context:** Checking a grant and then saving a renderer Yjs snapshot leaves a gap
between authority and persistence. An older background snapshot can also replace
accepted content. ADR-50's document-write tripwire requires a shared commit boundary.

**Decision:** The first editable document handle renders a host-owned plain-paragraph
editor. The guest receives an opaque handle and a current text projection, never a
Y.Doc or arbitrary update RPC. Saving prepares a clone and atomically compares the
exact page, private folder ancestry, active approval and current local overlay.
The same transaction commits the overlay, command count and attributed receipt.
Only accepted deltas enter the live document. A changed draft revision is a conflict;
concurrent CRDT changes merge without treating client IDs as authenticated authorship.

The versioned `document-overlay:v1:<encoded-node-id>` device-local record stores a
bounded full Yjs state. Memory and SQLite reads merge it with the base snapshot;
marked document writes merge prior, incoming and overlay state. The Electron data
owner hydrates acquired documents from this path and forwards accepted changes to
open renderers. Physical deletion removes the overlay. The data store subpath
exports the bounded encoding/merge/key helpers and structural snapshot comparator;
the untrusted extension loader does not expose those exports.

Folder/space grants select at most ten roots and 100 nested containers. Fresh
ancestry and deterministic owner-issued membership evidence constrain queries;
expiry and reparenting invalidate authority. Page text and private writes still need
exact-record grants. Private folder edits compare all ancestry evidence in the
committing transaction. Shared destinations remain denied.

**Tradeoff:** This is a conservative editor, not the general xNet editor contract.
Formatting and embeds remain read-only. Overlays retain CRDT history and stop at
128,000 bytes; there is no automatic compaction or document undo yet. Authority and
receipts are device-local. This adds neither remote revocation nor cryptographic
attribution of Yjs clients. Membership validation intentionally accepts fewer edges
than the core resolver, including an additional expiry check.

**Tripwire:** Before rich editor commands, shared document writes, raw updates,
overlay compaction, or a stable public SDK, prove the same atomic authority boundary,
concurrent-edit preservation and restart behavior for that path, and independently
review disclosure and resource limits. Revisit the overlay design when measured
history size blocks ordinary approved editing.

## ADR-52: Report observed agent phases in the local chat journal

**Status:** Accepted · 2026-10-20 · local prototype

**Context:** A streamed conversational reply can finish before the provider emits
its extension source. A generic “replying” label hides that work, while generated
progress prose could claim actions the host has never observed.

**Decision:** Add optional timestamped `activity` entries to the desktop
`CommunityAgentRun` contract. The host records connection, provider waiting,
reply streaming, extension generation and response validation once per phase.
Terminal state and publication remain authoritative. Old journals without this
metadata show their existing status without inventing a historical timeline.
The metadata remains device-local and carries no reasoning, source, tool payloads,
provider session IDs or credentials. The chat uses one compact current status
and optional details; completion leaves a receipt on the existing answer.

**Tradeoff:** This is a coarse timeline, not a measure of percent complete. Buffered
provider responses can omit intermediate phases. Validation does not imply an
extension has been compiled, tested, installed or granted data access.

**Tripwire:** Revisit the vocabulary and retention bounds before adding executable
tools, concurrent tasks, remote agent activity or a stable external activity API.
Every new reported action must have an observable host event and a tested terminal
state; provider-generated progress text alone is insufficient evidence.

## ADR-53: Share immutable chat extension source with explicit remix ancestry

**Status:** Accepted · 2026-10-20 · local prototype

**Context:** Device-local agent drafts cannot be reviewed by another conversation
member. A flat build history also loses which version a person intended to edit.

**Decision:** Share a bounded JSON attachment through the existing signed chat
message and blob paths. Format `xnet-chat-extension`, version `1`, carries one
source snapshot, title, summary, author, parent fingerprint and change note.
The SHA-256 version fingerprint covers those fields in a fixed key order, with
an absent parent encoded as null. The attachment MIME type is
`application/vnd.xnet.chat-extension+json`. Readers reject unknown fields, versions,
invalid UTF-8, content mismatches and payloads over 128,000 bytes. Source retains
the 24,000-character preview limit. The author must match the signed message's
creator; forwarding an unchanged third-party snapshot as your own is rejected.

Recipients explicitly review the source and save a private PluginSource copy.
They choose their own data permissions. Approval identity hashes the compiled build
and the version fingerprint together; identical code from another author cannot
reuse a grant. Legacy versions without lineage retain their build-bound grants.
Sharing never includes grants, runtime
credentials, document projections or task records. Installing stays device-local.
Remixing creates a new source version, attributed to the editor and linked to its
selected parent; existing versions remain unchanged through this UI. Missing
ancestors are labeled unavailable, never reconstructed from claims. A parent link
records claimed derivation, not independent proof of how code was written.

The optional desktop agent request `extensionRevisionId` selects a reviewed,
owned source record in the same conversation. The host validates and reads that
record, includes its bounded source as untrusted context, and records optional
`baseRevisionId` and `baseVersionId` on the run. It takes precedence over automatic
recent-draft context. Old requests and journals remain supported.

**Tradeoff:** This is a single-parent history without merges or dependency bundles.
Legacy builds retain their local node references. Receiving a child does not fetch
missing ancestors. Saved shares do not prove delivery, and source can contain
private literals even though data grants are excluded; the share confirmation asks
the user to review source. Branch browsing covers the latest 200 local copies and
reports truncation. Host resource limits and consent still apply to every build.

**Tripwire:** Revisit this format before publishing a stable extension ecosystem,
supporting forwarded third-party signatures, merges, multi-file packages, automatic
ancestor retrieval, or cloud catalogs. Require independent attribution review and
two-device delivery tests before claiming interoperable distribution.

## ADR-54: Keep shared extension development in authenticated chat records

**Status:** Accepted · 2026-10-22 · local prototype

**Context:** Sharing source copies does not give collaborators a common project,
execution policy, or the conversation that produced a particular version.

**Decision:** Add optional indexed development fields to ChatMessage. A version-1
JSON envelope carries a closed project, feedback, host offer, request, attempt, version,
withdrawal, or acceptance record. Each record's node ID binds its author, channel,
visible text, and canonical payload through SHA-256. Consumers verify the envelope,
identity, bounds, and relationships before using it. Redaction remains a message
operation. Changing hashed fields invalidates the record rather than rewriting a
previously accepted version. The existing source-attachment version-1 format stays
unchanged; project records separately carry up to four parent version-record IDs.

Only a device owner can grant use of their runtime. Device-local delegation names
one project and channel, requesters, an epoch, expiry, and request budget. Signed
peer requests must match that grant and current contributor membership. The host
serializes its queue, checks scope before dispatch and publication, and starts each
shared provider turn with fresh explicit context. Queued work survives restart but
requires a ready runtime; interrupted work requires an explicit retry. Host offers
advertise permission but never create it. Credentials and provider sessions stay local.

New requests carry ordered message IDs and revision digests frozen at submission.
The host rejects changed, removed, unfrozen, or cross-project context. The original
request stays immutable; withdrawing it and sending a new one records the revision.

Versions retain their source fingerprint, attributed request/attempt, parent IDs,
and reported message revisions. The history viewer checks current source-message
availability and redaction before displaying retained text. Published snapshots are
copies received by the conversation's existing audience: they cannot promise erasure
from other devices or cryptographic proof of provider execution. Future changes to
history retention must account for these already distributed copies. Sharing source
outside the project excludes its development history and local data grants.

Project creators accept versions through append-only acceptance records referencing
previously observed acceptances. Concurrent heads remain visible until explicitly
resolved. A host's queue is local serialization, not a distributed lock or an
exactly-once guarantee across disconnected hosts.

**Tradeoff:** This prototype supports top-level community membership and bounded
single-file extensions. It does not silently grant agent tool execution, shared-data
writes, installation, or inherited-community authority. Retained transcripts are
reported provenance; opaque model internals are outside the record.

**Tripwire:** Revisit before publishing a stable shared-development API, broadening
membership inheritance, adding automatic private-context inclusion, requiring hard
history erasure, or claiming distributed exactly-once execution. Require two-client
transport, conflicting-head, restart, and revocation evidence before release.

### ADR 55: Community dependency rooms for collaboration (prototype)

**Date:** 2026-10-22. **Status:** Prototype.

A channel share room does not carry the community and membership records needed
by a second client's authorization evaluator. Add `xnet-community-<spaceId>` as
a subscribe-only dependency room. It carries signed Space and SpaceMembership
changes, never arbitrary child content. Existing publish-wrapped node changes
and per-room sequence cursors are unchanged.

The first implementation supports top-level circles whose creator manages the
roster. Authenticated hosts require a current creator-issued membership and
reject a self-issued wildcard as sufficient permission to read the roster.
The creator comes from the ownership index pinned at first verified creation,
not an author selected by the lowest Lamport clock. Client writes and clears to
the dependency room are rejected; only the relay indexes its signed records.
Explicit anonymous development hosts retain their existing open-relay semantics.
A membership expiry or removal affects future reads after it is observed;
already received records cannot be recalled. This does not complete 0478's
private-community encryption or general inherited membership model.

**Tripwire:** Nested communities, delegated roster administrators, or a roster
larger than 2,000 people requires a reviewed dependency and authorization design
before expanding this protocol.

## ADR-56: Store chat preview assets as file references

**Status:** Accepted · 2026-10-22 · local prototype

The optional `image` and `media` fields on `MessageLinkPreview` carry existing
`FileRef` values. The sender resolves metadata and uploads preview bytes through
the existing blob service. Readers render those stored references. Existing
`imageUrl` records remain compatible; the desktop chat does not hotlink them.

Desktop resolution checks DNS and every redirect, pins the checked address to
the socket, and limits time, bytes, concurrent requests, and URLs per message.
Sending text does not wait for a preview. YouTube embeds load only after a click
and contact YouTube directly; they are not offline video copies. Readers validate
preview fields and never execute arbitrary provider HTML.

**Tradeoff:** Snapshots can become stale and consume blob storage. Images and
files share the conversation's current attachment permissions and retention
limitations. A preview is untrusted presentation, not proof of a site's identity.

**Tripwire:** Revisit before adding authenticated unfurling, automatic recipient
fetching, arbitrary provider embeds, or durable background retries. Require
two-device blob-delivery evidence before promising offline availability to every
conversation member.

## ADR-57: Pin approved desktop peers and isolate their text-chat records

**Status:** Accepted · 2026-10-22 · local prototype

The desktop uses Iroh ALPN `xnet/peer-chat/1` with a separate persistent transport
key bound by a signature to its existing xNet DID. A version-1 `xnet://peer#…`
invitation includes the endpoint ticket, conversation ID, expiry and random
join secret. The inviter approves the claimed peer identity before replication.
Transport authentication alone grants no access to the rest of the workspace.

Each device projects its own private space/channel membership locally. Only
bounded, signed ChatMessage changes authored by the pinned peer, with IDs under
that conversation's `iroh-` namespace, cross the connection. A Lamport/hash
cursor advances only after the receiver accepts the changes into NodeStore.
Both hub import and export paths exclude that namespace. Disconnect revokes
transport permission while retaining local history.

The default preview relay is invite-only, persists quota/admission state, and
forwards end-to-end encrypted traffic. It is a fallback data path, not an
offline mailbox. Direct paths are preferred when reachable. The Railway HTTP
deployment does not provide UDP address discovery, so cross-NAT direct rates
remain an empirical question. The prototype does not promise public scale,
anonymous networking, or encrypted SQLite files.

**Tradeoff:** The first transport supports two-person text chats. Groups,
attachments, agents and extensions need separate authorization and replication
designs. Bounded traffic can delay delivery, and changes to the pinned relay or
version-1 invitation format may require new invitations. The pinned native
binding also needs packaging validation beyond the tested Apple Silicon host.

**Tripwire:** Revisit before sharing group history, relaying media, adding offline
mailboxes, permitting agent actions from remote peers, or publishing a stable
cross-language wire API. Measure two-device direct/relay behavior and relay cost
before widening the current admission/traffic limits. A failed authorization or
hub-isolation negative control blocks release.

## ADR-58: Keep desktop social authentication separate from workspace keys

**Status:** Accepted · 2026-10-22 · local prototype

Native Bluesky sign-in runs in Electron main through the ATProto OAuth client,
using the system browser, PKCE, PAR and DPoP. Development uses a short-lived
loopback callback; packaged builds use the registered `fyi.xnet:/oauth/callback`
URI, matching the native client metadata.
The callback is bound to one transaction, the requested handle and the provider's
verified DID. Discovery uses bounded HTTPS requests with public DNS pinned to the
socket; redirects never forward credentials. The renderer receives public profile
metadata only. The initial scope is `atproto` (identity), and the temporary session
is revoked and discarded after verification. No provider token is persisted.

The verified profile is stored with the existing onboarding state. Linking a
different account requires an explicit disconnect. Social login neither replaces
the xNet signing key nor recovers an existing workspace. A handle typed into a
profile remains distinct from an OAuth-verified account on this device; this
ceremony does not publish a public provider-to-xNet binding.

Development uses ATProto's localhost metadata exception. Packaged builds use
`https://xnet.fyi/oauth/atproto-desktop-client.json`; that file must be published
before a distributed build can use it. The current Electron runtime constrains
the SDK version; runtime and authentication dependency upgrades need joint testing.

**Tripwire:** Persistent provider access, public identity discovery, a new provider,
or provider-driven recovery requires a separate consent, binding and revocation
design. A failed wrong-account, state-replay or callback-host negative control
blocks release.

## ADR-59: Bound private peer groups to a signed roster and an explicit host

**Status:** Accepted · 2026-10-22 · local prototype

Version-2 peer invitations add one group destination to the existing one-person
capability. The creator's pinned xNet DID is the group's authority. Each invite
is separately approved and each recipient has a separate authenticated transport
connection. The host signs a monotonically revised membership list, with at most
eight active members. Membership mutations are serialized; repeated approval is
idempotent. Other members cannot promote themselves or edit the roster.

The host forwards bounded original signed text changes over encrypted Iroh links.
Recipients verify the original author, conversation and signed roster before
projecting local membership and applying changes to NodeStore. A separate cursor
per author prevents a late-arriving author's lower Lamport clock from being
skipped. Signed display names can travel with the roster; OAuth tokens and other
workspace data cannot. Groups remain isolated from hub import and export.

The host is a participant and can read the group. It must be online to deliver
messages. A new member receives available history from current members; history
from departed authors is not newly replicated because current NodeStore author
permissions no longer authorize it. Removing a member stops future delivery and
submission through the host. It does not erase previously received copies. The
prototype supports 16 groups and 32 peer connections per profile and retains the
existing frame, traffic and relay limits.

**Tradeoff:** One host is a deliberate availability dependency, not a federated
administrator set or a general group-key protocol. Local projections do not grant
remote access to agents, attachments, extensions, unrelated channels or spaces.

**Tripwire:** Multiple hosts, host migration, offline mailboxes, larger groups,
departed-author history, media or extension replication requires a new authority
and history design. Verify removal, unauthorized authors, duplicate approval,
restart and late-author delivery before widening this prototype.

## ADR-60: Keep chats uniform while signing group access and channel scope

**Status:** Accepted · 2026-10-23 · local prototype

A group begins with one chat. Its first additional channel makes the group a
community in the interface; the original chat becomes General without moving
messages. All channels currently share membership and access. A private subset
uses a separate group. A thread is the existing flat `inReplyTo` relation within
one channel, with bounded database reads and a virtualized timeline.

Version-2 group manifests sign the access preset and channel list as well as the
roster. Child channel IDs are namespaced under their group ID. Replication checks
the original author and signed channel scope, and stores a cursor per channel and
author. Version-1 manifests remain readable. An existing private history cannot
be changed to public, or a public history made private, through an access toggle.

Version-3 links sign their complete invitation policy and derive a separate
connection for each requester. Approval links reveal no messages before host
approval. Public links allow read-only viewing without group membership;
posting requires joining the signed roster. Link revocation blocks new requests
without removing existing members or erasing received history. Public readers
still use an xNet device identity and count toward the bounded connection limit.
This is public access through the desktop, not anonymous website hosting.

The gateway's version-2 admission proof signs a maximum use count, capped at
eight. The existing membership, rate and byte limits remain in force. Older
relays keep single-device admissions with explicit UI feedback. Invitations
include direct addresses alongside the trusted relay so nearby devices can
connect when the relay is unavailable. A transport connection alone is not a
healthy relay: the desktop checks its health endpoint separately.
The preferred UDP port is persisted so direct routes survive restarts. A port
collision is reported explicitly when falling back to a new port; it can require
a fresh invitation if no other route is available.

Bluesky discovery reads public profile metadata and a pinned post through its
fixed public API origin. A published xNet link is an invitation shared by that
profile, not a verified provider-to-xNet identity binding. The recipient still
reviews the xNet key and membership request. No provider tokens or social writes
are involved. Other social services can carry the same invitation link.

**Tripwire:** Private channels inside a community, anonymous web readers, public
directories, non-expiring contact addresses, or public provider identity bindings
require a new authorization and discovery design. Failures of cross-channel,
pre-approval, read-only, link-revocation or restart tests block rollout. Publish
the gateway and invitation landing page separately before promising multi-device
relay onboarding or click-to-install links on the public website.

## ADR-61: Inspect extensions in disposable desktop test copies

**Date:** 2026-10-23

**Status:** Accepted for the local desktop prototype

Generated extension drafts pass through a bounded visual and interaction review
before being returned. The host runs the same worker sandbox and trusted view
renderer in a separate Chromium window with no preload, workspace identity,
personal data, persistence bridge, or external network access. It supplies actual
screenshots, visible control bounds, and errors to the selected agent. Inline
PNG/JPEG input is additive to the devkit turn contract; paths and remote image
URLs are not accepted by that API.

The agent can request only bounded clicks, text input, fixed viewport changes,
reset, or a full source revision. It never receives CDP, arbitrary JavaScript,
filesystem access, or native tools. Tests cannot grant permissions or install a
revision. Limits are twelve decisions, three revisions, sixty-four actions, and
the existing five-minute run deadline. Cancellation destroys the test window.

Only successful rendering and observed interactions on the final revision at
both supported widths can produce a checked report. The report records what
happened and its limits; it is not proof of general correctness. Extensions that
need personal data remain explicitly limited until a person grants access and
checks those operations. Existing per-version data permissions remain in force.

**Tripwire:** Testing against real user data, allowing native tools, running
unbounded action sequences, or sharing screenshots outside the selected provider
requires a new consent and isolation design. A mismatch between the checker and
the live renderer, a leaked workspace bridge, or a cancelled check continuing to
act blocks rollout.

## ADR-62: Browser-rendered extensions with brokered desktop capabilities

**Date:** 2026-10-23

**Status:** Accepted for the local desktop prototype

Desktop extensions render React DOM in a separate sandboxed `WebContentsView`.
This supersedes ADR-61's worker/tree renderer for desktop previews and test copies;
the previous renderer remains the non-desktop fallback. HTML, CSS, SVG, canvas,
and browser controls do not require an expanded data grant. Dependencies are
bundled by the host; guest code cannot install packages or run lifecycle scripts.

Each running version has a fresh, non-persistent Chromium session. Node integration
is off, context isolation and process sandboxing are on, and the preload exposes
only a fixed message interface. Main validates the sender and its owning workspace.
Network resources, nested frames, navigation, popups, downloads, device permissions,
browser dialogs, and display capture are denied. WebRTC non-proxied UDP is disabled and the session
uses a non-forwarding local proxy in addition to URL filtering and CSP. A watchdog
closes an unresponsive surface. Closing the workspace or preview revokes its handles.

The existing xNet brokers remain the authority for data. Document saves use approved
handles, bounded plain text, revisions, and the existing durable commit checks.
Native file APIs require a trusted user gesture and a host-owned file dialog. Read
handles identify only a chosen file; editing requires separate consent. Writes reject
changed/replaced or multiply-linked files. No guest-controlled path, shell, raw IPC,
or Electron object crosses the boundary. Native access lasts only for that preview.

Self-checking uses the same browser surface. Its enclosing controller has only the
surface-management preload, and its native/data capabilities are denied. An isolated
preload gathers control geometry; the agent receives screenshots and bounded actions.
Tests of real private data or native grants cannot be reported as successful by this
loop. Test authority never carries into a preview with real data.

**Tripwire:** Remote dependencies, network egress, directories, persistent file grants,
shell execution, arbitrary native APIs, or enabling agent harness tools require their
own capability and consent design. A cross-surface request, surviving revoked handle,
network leak, privileged preload, or preview/checker mismatch blocks rollout. This
prototype is not a claim of zero vulnerabilities; runtime updates and independent
security review remain release requirements.

## ADR-63: Ephemeral multiplayer rooms for desktop extensions

**Date:** 2026-10-24

**Status:** Accepted for the local desktop prototype

A sandboxed extension can request one temporary Iroh room through a narrow native
broker. Three.js is pinned and bundled with the host. Browser network access,
WebRTC, Node, Electron objects and arbitrary relay URLs remain unavailable to guest
code. This adds the explicit network capability contemplated by ADR-62; it does not
change the existing data or file grants.

Hosting or joining requires a trusted user gesture followed by a native consent
sheet. The sheet identifies the extension, discloses network-address exposure and
public relay use, and explains that the extension can transmit data it has already
been allowed to read. A grant belongs to this running surface, expires after one
hour, and is revoked on leave, stop, navigation or window close. It is not restored
with an installed extension. A test copy cannot obtain the grant.

Rooms use ephemeral transport identities and `xnet/extension-room/1` ALPN. An
invitation contains a random room ID, a 256-bit bearer secret, the SHA-256 of the
compiled extension source, the host endpoint ticket and an expiry. The host checks
the secret, room and source hash after QUIC authenticates the peer endpoint. These
transport IDs do not establish a person's social identity. Anyone holding the
invitation and matching code can join; there is no public discovery. Invitations
are pasted into the same extension, not routed by the app's existing contact-link
onboarding. Identical source does not guarantee compatible future runtime releases.

Four players share a host-and-guests topology. Client datagrams go only to the host;
host datagrams go to its guests. The native broker supplies sender identity, accepts
at most 30 sends per second, limits frames to 1,000 bytes, rejects stale sequences,
and bounds pending handshakes and accepted peers independently. Connections without
updates or heartbeats are closed. Relay destinations come only from the pinned Iroh
production relay map; an invitation cannot specify an arbitrary HTTP relay. Direct
addresses are connection hints, authenticated against the ticket's endpoint key.
The broker creates no chat records and exposes no general socket API.

The example runs a host-authoritative simulation with 10 Hz snapshots and client
inputs, then interpolates the 3D view locally. Frame loss is expected. Host cheating,
host migration, matchmaking, cross-version play and durable scores are outside this
prototype. Default public relays are best-effort. A relay can carry game bandwidth,
not merely discovery traffic; the preview reports when no relay is advertised.
The existing authenticated xNet chat relay is not reused by these ephemeral endpoints.

An agent may inspect the local practice view, but the checker marks multiplayer
verification as limited even when the agent never clicks Host. Real network tests
require separate consenting peers. Existing xNet/file authority remains independently
scoped and revocable.

**Tripwire:** More than four players, sustained larger payloads, host migration,
verified contact membership, persistent grants, a browser/WebRTC adapter, cross-version
compatibility or use of the authenticated xNet relay requires another protocol and
consent review. A fifth admitted player, unbounded handshake work, unexpected relay,
network activity after revocation, or a visual test reported as proof of multiplayer
blocks rollout. Adversarial review and multi-network verification remain required
before presenting this as production-ready networking.

## ADR-64: Separate community file delivery from hosted discovery

The community prototype reserves HTTPS share links for public catalog records, opaque private file handles and room invitations. A single hub can run tracker and relay roles on the same origin. Public seeder leases expire. A private lookup requires a device signature, and the serving desktop checks room membership for each private chunk. Iroh can relay chat and connection setup. The desktop sends media on a direct-only endpoint. One volume backup preserves the hub's authorities, admission state and catalog.

**Tripwire:** Reopen the direct-only media choice if invited peers on separate residential networks regularly succeed at chat but fail at playback. Measure failed direct routes and price an explicitly budgeted media relay before changing the default.

## ADR-65: Let room peers share history with a five-minute permission

The community desktop fetches room history over authenticated direct connections. The room owner signs each message’s sequence and the current list of permitted devices and hidden messages. Readers and serving peers check with the owner for each page. If the owner is unreachable, both may use their signed permission for up to 300 seconds from issuance. Relays may forward live sends and connection setup. History pages stay on participants’ devices. A disconnected member may continue reading during the remainder of its grant following a removal.

**Tripwire:** Revisit this choice before extending the five-minute window, allowing offline grants to admit new members, or storing or forwarding history on a hosted service. A page returned to an unauthorized device or after its permission expires blocks rollout.

## ADR-66: Coordinate public post copies separately from room history

The community tracker accepts signed, expiring inventories for public text posts. Offers reserve replica slots without advertising an available source. The receiving desktop controls its byte budget, verifies the original author's signature, and chooses which followed authors to retain. Room history and membership never enter this inventory. Existing room reads continue to require an authorized peer. An online seeder count is a recent claim, not a durability guarantee.

**Tripwire:** Revisit the protocol before indexing private inventories, treating a claimed copy as a paid storage commitment, or using automatic placement for large media. If three recent claims repeatedly produce no reachable source, measure reachability and add independent verification before increasing the replica target.
